# Real-time on-device instrument removal and music detection: models, runtimes, DSP (state of the art as of Nov 2026)

Scope: models and techniques that can (a) remove musical instruments from a live audio stream while keeping human voice (speech or singing) and (b) cheaply detect whether music/instruments are present, running on a smartphone CPU/GPU/NPU with <100–200 ms added latency. Notes are organised by key question; a consolidated comparison table is in the first section. Web-search budget ran out near the end of the research, so a few items (Google's own Audio Magic Eraser write-up, Apple's Audio Mix support page, LiteRT NPU docs, YAMNet .tflite file size) could not be verified and are listed under Gaps.

## Key Question 0: Consolidated comparison table (all candidates)

### Takeaway
No released, pretrained, commercially-licensed model exists today that does causal vocals-vs-instruments separation at phone-feasible compute; the causal MSS research models (Band-SCNet, RT-STT, ADI's DSP model, HS-TasNet) show it is technically achievable (5–8 dB SDR at 23–92 ms latency, 0.1–2.6 M params) but none ship weights. Causal speech-enhancement models (DeepFilterNet3, GTCRN) are the only drop-in, permissively-licensed, mobile-proven option, and they treat music as noise; cheap music detection is solved (YAMNet via MediaPipe: 12 ms per ~1 s window on Pixel 6 CPU).

### Inferences
- Only the speech-enhancement family (DeepFilterNet3, GTCRN, RNNoise) ticks every box the brief needs — causal, <50 ms, tiny compute, permissive license, pretrained weights, existing Android/iOS builds — but they are trained to keep *speech* and suppress everything else, so singing voice is at risk (see KQ2).
- Every causal music-separation paper (HS-TasNet, Band-SCNet, RT-STT, ADI) withholds weights; shipping true vocals-vs-instruments separation in real time means training your own causal model (e.g., Band-SCNet or ADI recipe on MUSDB18-HQ + extra data) and then porting it.

### Gaps
- No source gives a vocals-only SDR for a causal model on a real phone; all RTF numbers are desktop CPU/GPU or a DSP.
- DeepFilterNet3's exact parameter count/MACs were not in the show-and-tell paper or README (only DFN1's 1.8 M / 0.35 GMAC/s and RTF 0.19).

## Key Question 1: Music source separation — which models are feasible on mobile, which have streaming/causal variants, and what latencies/SDRs do 2022–2026 papers report?

### Takeaway
Offline state-of-the-art (BS-RoFormer, Mel-RoFormer, SCNet, HT Demucs) needs seconds of context and tens of millions of parameters; the published causal alternatives land at 4.7–7.8 dB SDR with 23–92 ms latency, and the best trade-off (Band-SCNet: 7.79 dB, 2.59 M params, 92 ms) still needs 17.6 GFLOPs/s and has no public weights.

### Cited Findings
- Hybrid Transformer Demucs "achieves a SDR of 9.00 dB on the MUSDB HQ test set"; hybrid transformer models have a maximum segment length of 7.8 s; CPU processing takes "about 1.5 times the track's duration"; GPU needs ≥3 GB (≈7 GB default); code MIT; README mentions only a third-party "realtime Demucs" model in Neutone's plugin — [facebookresearch/demucs](https://github.com/facebookresearch/demucs)
- Neutone v1.4 (July 2023) added a "Demucs StemSeparation" model with "playback delay significantly reduced" and DAW latency compensation; no latency figure published — [Sonicstate](https://sonicstate.com/news/2023/07/06/neutone-updated-to-v14-)
- Open-Unmix is a three-layer BiLSTM; bidirectional design "cannot be used in an online/real-time manner"; a unidirectional model can be trained but no pretrained one is listed; umxl weights are CC BY-NC-SA 4.0; vocals SDR umx 6.32 / umxhq 6.25 / umxl 7.21 — [sigsep/open-unmix-pytorch](https://github.com/sigsep/open-unmix-pytorch)
- Spleeter code is MIT; 2/4/5-stem models; "100x faster than real-time when run on a GPU" — [deezer/spleeter](https://github.com/deezer/spleeter)
- On an (unnamed) mobile device, "Open-Unmix and Spleeter consumed 94.6 and 23.32 msec respectively per second of input"; Demucs "was not able to be implemented on the mobile device because the model size is beyond capacity" — [GSEP, arXiv 2010.12139](https://arxiv.org/pdf/2010.12139) (2020-era models)

- SCNet: 9.0 dB SDR on MUSDB18-HQ without extra data; "CPU inference time is only 48% of HT Demucs" — [arXiv 2401.13276](https://arxiv.org/abs/2401.13276)
- Band-SCNet Table 1 (MUSDB18-HQ, no extra data): HT Demucs 7.52 (42.0 M), Hybrid Demucs 7.64 (83.6 M×3), DTTNet 8.06 (5.0 M×4), BSRNN 8.24 (40.14 M×3), SCNet 9.00 (10.08 M), SCNet-large 9.69 (42.18 M), BS-RoFormer 9.80 (72.2 M×3); causal: HS-TasNet 4.65 (42 M, 23 ms), Wave-U-Net [Kim & Kang 2023] 6.47 (5.7 M, 23 ms), Online SCNet 7.09 (4.36 M, 12.25 GFLOPs/s, 92 ms, RTF 0.428), Band-SCNet 7.79 (vocals 8.74, drums 9.44, bass 7.13, other 5.87; 2.59 M, 17.59 GFLOPs/s, 92 ms, RTF 0.478 single-thread i7-13700H) — [Interspeech 2025 PDF](https://www.isca-archive.org/interspeech_2025/yang25d_interspeech.pdf)

- HS-TasNet (L-Acoustics, ICASSP 2024): latency 23 ms (1024/512 at 44.1 kHz); overall SDR 4.65 (vocals 5.13, drums 5.22, bass 4.59, other 3.64) on MUSDB; 5.55 (vocals 5.97) with 150 extra songs; HS-TasNet-Small 16 M params; per-23 ms-block inference on i7-12850HX: HS-TasNet 9.10 ms (1 core)/4.26 ms (4 cores), Small 3.98/1.83 ms; design rule "average inference time on 4 CPU cores should be less than 50% of the hop size"; causal X-UMX scores 3.93 at 23 ms and 4.57 at 93 ms vs 5.79 offline; MUSHRA: DemucsV4 significantly better than all real-time models; HS-TasNet ≈ DemucsV2 — [L-Acoustics PDF](https://www.l-acoustics.com/wp-content/uploads/2024/04/real_time_demixer_2024_04_19.pdf), [arXiv 2402.17701](https://arxiv.org/abs/2402.17701)

### Inferences
- Scaling Band-SCNet's RTF 0.478 (single desktop core at 2.4 GHz+) to a phone big core suggests RTF ≈1–2 single-threaded; it would need multi-threading, GPU, or NPU to run live, and int8 is risky (RT-STT's int8 degraded).
- ADI's 131 K / 1.89 GMAC/s model (vocals ~5–6 dB) is the only one with a demonstrated hard-real-time budget; it runs comfortably on any phone CPU but will leave audible bleed.
- The ADI finding that chunk-trained models collapse in true frame-by-frame streaming means a developer cannot simply run an offline model on short chunks; the model must be trained with streaming state.

### Gaps
- No causal MSS paper has released weights; no measurements on Snapdragon 8 Gen 2/3, Tensor or A17/A18 exist for any causal MSS model.
- The HS-TasNet and Band-SCNet licenses are unstated (no code).

## Key Question 2: Speech-enhancement vs singing — do noise suppressors remove music, and do they keep singing voice? Dialogue-enhancement systems

### Takeaway
Speech enhancers are trained to "preserve primary speaker speech while suppressing everything else", so they do remove music under speech, but the DNS corpora only added singing in 2021 and no source reports a singing-preservation metric; broadcast dialogue separators (Fraunhofer Dialog+/ConcateNet, Sony) exist but are proprietary, file-based production tools.

### Cited Findings
- DNS Challenge goal: "preserve primary speaker speech while suppressing everything else" — [Microsoft DNS ICASSP 2023](https://www.microsoft.com/en-us/research/academic-program/deep-noise-suppression-challenge-icassp-2023); earlier challenge noted "noticeable WAcc and SIG degradation due to over-suppression" — [arXiv 2009.06122](https://arxiv.org/pdf/2009.06122)
- DNS 2021 added 10.1 h of clean singing (VocalSet, CC BY 4.0, 20 professional singers) to the clean-speech set and the test set includes "emotional speech and singing in the presence of background noise" — [arXiv 2009.06122](https://arxiv.org/pdf/2009.06122), [Interspeech 2021](https://www.isca-archive.org/interspeech_2021/reddy21_interspeech.pdf)
- DeepFilterNet3 is trained on "the multilingual DNS4 dataset" — [arXiv 2305.08227](https://ar5iv.labs.arxiv.org/html/2305.08227); facebook/denoiser trains on DNS and Valentini (speech datasets) with no music/singing mention — [GitHub](https://github.com/facebookresearch/denoiser)
- Albayzin 2020 ASR: running TV audio through Demucs and keeping only the voice stem "significantly eliminated the background music, while maintaining relatively good quality in the original voice"; an extra denoiser on already-clean audio raised WER by 1.6 % absolute — [arXiv 2101.12729](https://arxiv.org/pdf/2101.12729)
- A VAE separator "removes the music … however, replaces the music content with random noise instead of silence" — [arXiv 1909.11727](https://arxiv.org/pdf/1909.11727)
- Causal BSRNN for speech: DNS-2020 no-reverb PESQ-NB causal 3.14, causal BSRNN-S 3.26, non-causal 3.32 — [arXiv 2212.00406](https://arxiv.org/pdf/2212.00406)
- Fraunhofer MPEG-H Dialog+: "deep neural network performing dialogue separation … trained using supervised regression"; "deep fully-convolutional structure in the STFT domain"; combines separation with global and time-varying background attenuation; training data mostly WDR/BR broadcasts; deployed as ARD "Klare Sprache"; first field tests Sept 2020; 83 % of >2,000 survey participants liked it — [arXiv 2112.09494](https://arxiv.org/abs/2112.09494), [Fraunhofer](https://www.iis.fraunhofer.de/en/profil/jb/2022/ai-technology-for-clear-tv-dialogue.html)
- Dialog+ is a file-based, production-side tool sold via Telos Alliance's Minnetonka AudioTools Server; presets for documentaries, music films, sports; no real-time or consumer-device statement — [Fraunhofer audio blog](https://www.audioblog.iis.fraunhofer.com/?p=7749)
- ConcateNet (2024): dialogue separation "isolating a dialogue signal from a mixture, such as a movie or a TV program", trained on a noise-reduction dataset, generalises better than noise-reduction baselines on out-of-domain broadcast material — [arXiv 2408.08729](https://arxiv.org/abs/2408.08729)
- Commercial "remove music, keep voice" tools (LALAL.AI Voice Cleaner etc.) are vendor claims without published evaluation — [LALAL.AI](https://www.lalal.ai/voice-cleaner/)
- Samsung Galaxy S26 Audio Eraser: "real-time separation of sound into six distinct layers: voice, music, wind, nature, crowd, and other noises", works "across 3rd party apps like YouTube, Instagram, and Netflix", runs on-device; Samsung warns "accuracy of results is not guaranteed" — [Samsung Newsroom (global)](https://news.samsung.com/global/faster-real-time-enhanced-audio-eraser-with-the-galaxy-s26-series), [Samsung Research interview](https://news.samsung.com/global/interview-designing-with-the-user-in-mind-inside-the-advanced-research-behind-audio-eraser), [Neowin](https://www.neowin.net/news/samsung-evolves-audio-eraser-into-real-time-sound-control-on-galaxy-s26/) (newsroom pages timed out on fetch; quotes via search snippets); S25 launch version was post-recording only — [Android Central](https://androidcentral.com/phones/how-to-use-audio-eraser-on-the-samsung-galaxy-s25); One UI 8 beta brought a live mode — [Android Central](https://www.androidcentral.com/phones/samsung-galaxy/one-ui-8-beta-makes-ditching-background-noise-from-your-audio-and-video-way-easier); battery "slightly increased" when running continuously, no figures published — [Laptop Mag](https://www.laptopmag.com/phones/android-phones/samsung-galaxy-audio-eraser-review)
- Pixel Audio Magic Eraser: post-capture; categories Speech, Wind Noise, Music, Nature, Noise; analysis "might take a few minutes depending on length" — [Tom's Guide](https://tomsguide.com/how-to/how-to-use-audio-magic-eraser-on-google-pixel), [Android Central](https://www.androidcentral.com/apps-software/how-use-audio-magic-eraser)
- Apple iPhone 16 Pro "Audio Mix" "uses machine learning to identify and separate background elements from speech", applied "after capture" — [Apple Newsroom](https://www.apple.com/newsroom/2024/09/apple-debuts-iphone-16-pro-and-iphone-16-pro-max/); Voice Isolation for cellular calls (iOS 16.4) blocks ambient sound in real time using on-chip ML — [iMore](https://imore.com/iphone/how-to-enable-cellular-voice-isolation-on-iphone-with-ios-164)

### Inferences
- For *speech* over a music bed (lectures, reels with voice-over, Quran recitation with background music), a causal SE model will largely strip the music; residual "musical-noise"-like artifacts and some speech dulling are the expected failure modes.
- For *singing* (nasheed) with instruments, SE models are the wrong tool: their training objective treats non-speech as noise, and even with VocalSet in training, sustained vowels/vibrato with harmonic accompaniment are likely to be partly suppressed. This needs an MSS vocals model, which is the harder, heavier problem.
- Samsung's S26 feature is the existence proof that six-way real-time separation of arbitrary app audio on a phone is feasible, but it is OEM/system-level and undocumented.

### Gaps
- No published metric for how much singing voice is retained by DeepFilterNet3/GTCRN/RNNoise, nor any "speech + music" SI-SDR benchmark for SE models.
- Whether Dialog+/ConcateNet treat sung vocals as "dialogue" is not stated in accessible sources.
- Sony dialogue-enhancement model details were not found before the search budget ran out.

## Key Question 3: Music/instrument detection ("mute when music is playing")

### Takeaway
YAMNet through MediaPipe's Audio Classifier is the proven cheap detector (3.7 M params, ~1 s windows, 12 ms per inference on Pixel 6 CPU, Apache 2.0); distinguishing a cappella/nasheed from instrumental music needs a vocal-vs-instrumental classifier (Essentia `voice_instrumental`, ~790 K params) or a separate-then-measure pipeline, and nobody publishes a dedicated "a cappella vs accompanied" model.

### Cited Findings
- YAMNet: MobileNet_v1, ~3.7 M weights, ~69.2 M multiplies per 960 ms frame, 521 AudioSet classes, 16 kHz mono, 0.96 s patches overlapping 50 %, ≥975 ms needed for the first output; AudioSet mAP 0.306; Keras-2 only — [tensorflow/models README](https://github.com/tensorflow/models/blob/master/research/audioset/yamnet/README.md); repo license Apache 2.0 — [LICENSE](https://github.com/tensorflow/models/blob/master/LICENSE)
- MediaPipe Audio Classifier: YAMNet is the only/recommended model; input 1×15600 samples (≈975 ms at 16 kHz); Pixel 6 CPU latency 12.29 ms (GPU n/a); AUDIO_STREAM mode is asynchronous with a result callback; "Music" is label index 137 — [Google AI Edge](https://developers.google.com/edge/mediapipe/solutions/audio/audio_classifier); Android sample classifies 16 kHz mic audio in one-second chunks — [GitHub](https://github.com/google-ai-edge/mediapipe-samples/tree/main/examples/audio_classifier/android)
- Qualcomm AI Hub lists YamNet (audio classification) and Silero-VAD but no audio-enhancement/separation model; repo BSD-3 — [quic/ai-hub-models](https://github.com/quic/ai-hub-models)
- Essentia `voice_instrumental` classifiers (MusiCNN-MSD, MusiCNN-MTT ~790 K params, VGGish 62 M) report 0.98 normalised accuracy in 5-fold CV before final training; 16 kHz; real-time simultaneous-classifier tutorial — [Essentia Labs](https://mtg.github.io/essentia-labs/news/tensorflow/2020/01/16/tensorflow-models-released), [tutorial](https://essentia.upf.edu/tutorial_tensorflow_real-time_simultaneous_classifiers.html)
- inaSpeechSegmenter (MIT, CNN): speech/music/noise segmentation; "speech over music or noise counts as speech, and singing voice counts as music"; MIREX 2018 speech-detection winner; file-based — [GitHub](https://github.com/ina-foss/inaSpeechSegmenter)
- Amazon catalog-scale instrumental detection: source-separate, quantify singing on the vocals track, then run an instrument-detection model — [Amazon Science PDF](https://cdn.amazon.science/5d/00/72f7e0c04fe99fc567cef1da5163/a-novel-method-to-detect-instrumental-music-in-a-large-scale-music-catalog.pdf)
- Online, loudness-invariant vocal detection with an LSTM over a compact feature set — [Lehner et al.](https://silicon-austria-labs.elsevierpure.com/en/publications/online-loudness-invariant-vocal-detection-in-mixed-music-signals); pitch-based features "discriminated poorly between the voice and loud pitched instruments" — [Interspeech 2009](https://www.isca-archive.org/interspeech_2009/rao09_interspeech.html)
- Classical speech/music discrimination: AdaBoost on 20 ms frames 88 %, 93 % with 800 ms smoothing — [ISMIR 2005](https://archives.ismir.net/ismir2005/paper/000065.pdf); feature-combination method >99 % "even for severely degraded and noisy signals", low complexity suitable for real time — [EURASIP 2009](https://asmp-eurasipjournals.springeropen.com/articles/10.1155/2009/239892); GTZAN speech/music set has 128 clips — [GitHub](https://github.com/r10a/music-speech-classifier)
- "HaramMute" is a browser extension (Chrome ~20 K users, Firefox/Android) that removes background music from YouTube and talks to `api.haram-mute.com` (server-side) — [Chrome Web Store](https://chromewebstore.google.com/detail/harammute-remove-backgrou/bbkbpldbnkoncockinoapcmbiijejgpn), [extscope](https://extscope.org/extension/bbkbpldbnkoncockinoapcmbiijejgpn); "MusicRemover" pairs the extension with a desktop app that does on-device separation — [Chrome Web Store](https://chromewebstore.google.com/detail/pljjgbebgcpplkcmggdemopekpennmfc)

### Inferences
- Detection latency is dominated by the ~1 s window, not the 12 ms inference; a "mute when music" mode will react roughly 0.5–1 s after music starts unless the window is shortened (with accuracy loss).
- For nasheed-vs-music, combine YAMNet's "Music"/"Singing"/instrument-family classes with a vocal-vs-instrumental head; or run a cheap separator and measure energy in the non-vocal stem (Amazon's approach) — the latter is the only robust route for "voice-only vs voice+instruments".
- inaSpeechSegmenter's labelling convention (singing = music) makes it unsuitable as-is for keeping nasheeds.

### Gaps
- YAMNet .tflite file size in MB could not be verified (Kaggle page did not render; the brief's "3.7 MB" is unconfirmed — the 3.7 M figure is the weight count).
- No benchmark of YAMNet/Essentia on a cappella vs accompanied material, and no latency/accuracy figures for Essentia models on phones.

## Key Question 4: Runtimes — streaming/stateful audio support on LiteRT, ONNX Runtime, ExecuTorch, Core ML, Qualcomm/MediaTek/Samsung NPUs

### Takeaway
All major runtimes run streaming audio models if the recurrent state is exported as explicit inputs/outputs (hidden state inside the module silently resets per call on ONNX/LiteRT/ExecuTorch); NNAPI is deprecated since Android 15, so NPU access now goes through LiteRT/ExecuTorch vendor backends or ORT's QNN EP, whose RNN support is partial (GRU unrolled, no dynamic sequence length).

### Cited Findings
- Stateful-LSTM model card: TorchScript keeps `self.hidden` inside, but "its ONNX, LiteRT, and ExecuTorch exports reset to a zero state on every block", so state must be moved to graph inputs/outputs; after that fix LiteRT matches ONNX Runtime to ~7e-7 — [HF anira-project/stateful-lstm](https://huggingface.co/anira-project/stateful-lstm); RAVE model ships ORT/LiteRT/ExecuTorch variants at 1024 samples/call, 44.1 kHz — [HF anira-project/rave-djembe](https://huggingface.co/anira-project/rave-djembe)
- Mobile ORT noise-suppression practice: pre-allocate tensors and feed LSTM states back each call — [HackerNoon](https://hackernoon.com/mobile-ai-with-onnx-runtime-how-to-build-real-time-noise-suppression-that-works)
- NNAPI "was deprecated in Android 15"; Google "expect[s] the majority of devices in the future to use the CPU backend" and recommends migrating to e.g. the TF Lite GPU runtime — [Android NDK docs](https://developer.android.com/ndk/guides/neuralnetworks)
- ONNX Runtime QNN EP: GRU supported on CPU (FP32) and HTP (QDQ/FP16) with "time steps always unrolled", no layout=1, no dynamic sequence lengths (v2.4.0); quantized GRU on HTP in v2.7.0; Loop/If unsupported — [onnxruntime-qnn v2.4.0](https://github.com/onnxruntime/onnxruntime-qnn/releases/tag/v2.4.0), [v2.7.0](https://github.com/onnxruntime/onnxruntime-qnn/releases/tag/v2.7.0), [QNN EP docs](https://onnxruntime.ai/docs/execution-providers/QNN-ExecutionProvider.html)
- ExecuTorch backends: XNNPACK (all, CPU), Core ML (iOS/macOS NPU/GPU/CPU), Vulkan (Android GPU, mature), Qualcomm (Android NPU), MediaTek (Android NPU), Samsung Exynos (Android CPU/GPU/NPU), Arm VGF, Cadence DSP, etc.; unsupported ops fall back to CPU via partitioner priority — [ExecuTorch docs](https://docs.pytorch.org/executorch/stable/backends-overview.html)
- 2026 Android overview lists LiteRT 2.3 (CompiledModel API), ONNX Runtime Mobile, ExecuTorch 1.5 "now stable" (secondary source) — [Forasoft](https://www.forasoft.com/blog/article/neural-networks-on-android-369); ExecuTorch paper reports XNNPACK delegate "extremely strong performance relative to LiteRT and ONNX for CPU inference" (vision/LLM, not audio) — [arXiv 2605.08195](https://arxiv.org/pdf/2605.08195)
- Arm KleidiAI is enabled by default in ExecuTorch 0.7 and integrated into LiteRT via XNNPACK; >20 % faster prefill on Galaxy S24+ (LLM, vendor figures) — [Arm blog](https://developer.arm.com/community/arm-community-blogs/b/ai-blog/posts/llm-inference-llama-quantized-models-executorch-kleidiai), [Arm Kleidi](https://www.arm.com/kleidi)
- Core ML stateful models require iOS 18 / macOS 15 and `mlprogram`; declare via `register_buffer` + `ct.StateType`; runtime `make_state()` passed to `predict()`; Neural Engine not discussed in the docs — [coremltools](https://apple.github.io/coremltools/docs-guides/source/stateful-models.html); Silero-VAD CoreML port keeps h/c states as explicit I/O with a 32 ms streaming variant — [HF](https://huggingface.co/aufklarer/Silero-VAD-v6.2.1-CoreML); `.cpuAndNeuralEngine` gives best energy efficiency but Core ML silently routes unsupported ops to GPU — [DEV post](https://dev.to/software_mvp-factory/wiring-apples-neural-engine-to-core-mls-stateful-models-24m1) (blog, unverified)
- sherpa-onnx supports speech enhancement with GTCRN (`gtcrn_simple`) and DPDFNet (8/16/48 kHz) with a "Streaming speech enhancement" C API; project targets Android, iOS, Flutter, HarmonyOS, WebAssembly — [sherpa-onnx docs](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/index.html)
- Qualcomm AI Hub previously listed facebook_denoiser (18.9 M params, source CC-BY-NC-4.0, Galaxy S23/S24, QCS8550) — [AI Hub](https://aihub.qualcomm.com/models/facebook_denoiser) (page returned 404 when fetched; not in the current model list — [repo](https://github.com/quic/ai-hub-models))
- Platform audio capture: Android AudioPlaybackCapture (Android 10+) requires RECORD_AUDIO, a user-consented MediaProjection token, and the source app not opting out (`allowAudioPlaybackCapture=false` means "audio played by the application will never be captured by non system apps"); usages can be excluded — [Android docs](https://developer.android.com/media/platform/av-capture), [AOSP commit](https://gitlab.e.foundation/e/os/android_frameworks_base/-/commit/4fd496d8bfef0511db76fd24624bee1bccce885f)
- iOS: ReplayKit broadcast extensions deliver only the mixed system stream; "it is not possible to capture application audio produced by AVPlayer, by Safari video playback … or by the Music app" — [Twilio](https://github.com/twilio/video-quickstart-ios/blob/master/ReplayKitExample); capture runs in a daemon so "hosting apps have no privileges to the broadcasted video and audio contents" — [Apple Platform Security](https://support.apple.com/guide/security/seca5fc039dd/web); developer-forum question on receiving other apps' audio has no supported answer — [Apple Forums](https://developer.apple.com/forums/thread/832464)

### Inferences
- A GRU-based model (DeepFilterNet, GTCRN, ADI's design) is the safest NPU-portable recurrence; LSTMs with growing cell state and dynamic lengths are the usual export casualties.
- Practical runtime pick: ONNX Runtime (XNNPACK CPU) for a single binary on both platforms, ExecuTorch when you want vendor NPUs via one toolchain, Core ML stateful models on iOS 18+.
- The hard blocker for an "always-on app processing all device audio" is not the model but the OS: Android only gives a *copy* of other apps' audio (and only if they allow capture), and iOS offers no supported path at all; Samsung's S26 feature works because it is system-level.

### Gaps
- No head-to-head mobile benchmark of a streaming audio model across LiteRT/ORT/ExecuTorch was found; LiteRT's NPU ("LiteRT Next") documentation and Samsung ENN SDK details were not retrieved before the search budget ran out.
- ORT QNN EP LSTM support status was not found (only GRU).

## Key Question 5: Classical / cheap DSP alternatives (center-channel, spectral gating, HPSS, REPET, pitch-based)

### Takeaway
Classical methods are real-time and free but only weakly hide instruments: center-channel cancellation removes everything panned centre (bass, kick, snare) and collapses with millisecond channel offsets or reverb; REPET/HPSS/low-rank methods have online variants but target repeating or percussive accompaniment, not general instrument removal.

### Cited Findings
- Phase inversion to remove centre content "also cancels a bass part panned to the center, along with everything else panned dead center" — [recording.org](https://recording.org/comment/isolating-mono-stereo-master-file-1); "there is no combination that can produce center-panned vocal isolation using simple channel mixing" — [Audacity forum](https://forum.audacityteam.org/t/center-panned-vocal-isolation/29719)
- "If the signal in one of the channels is delayed by even a millisecond or its phase is disrupted, the center will drift or disappear entirely" — [MVSEP](https://mvsep.com/algorithms/125); pan, delay, reverb and track fidelity determine effectiveness — [iZotope RX Center Extract](https://s3.amazonaws.com/izotopedownloads/docs/rx700/en/center-extract/index.html)
- Pre-deep-learning real-time MSS (Azimuth Discrimination and Resynthesis) used 93 ms STFT windows → 93 ms latency; an MLP at 23 ms did singing-voice separation for cochlear-implant remixing — [HS-TasNet paper intro](https://www.l-acoustics.com/wp-content/uploads/2024/04/real_time_demixer_2024_04_19.pdf)
- REPET assumes the accompaniment repeats (typical of pop); a real-time extension exists; REPET-SIM "can be easily implemented online" — [Lead/accompaniment separation survey, arXiv 1804.08300](https://arxiv.org/pdf/1804.08300), [REPET page](https://users.cs.northwestern.edu/~zra446/repet.html)
- Realtime HPSS with sliding STFT and causal median filter: percussive separation "acceptable" — [sevagh/Music-Separation-TF](https://www.github.com/sevagh/Music-Separation-TF); online low-rank (accompaniment) + sparse (vocal) decomposition — Sprechmann et al. ISMIR 2012 (cited in the survey above)
- Spectral-subtraction trade-off: "if too much noise is subtracted, it creates speech distortion … if less noise is subtracted, the enhanced speech remains noisy" — [arXiv 1802.02665](https://arxiv.org/pdf/1802.02665)

### Inferences
- Mid/side attenuation can be a useful *first stage* (cheap, zero-latency) for wide-panned instruments, but it cannot be relied on to hide a centred bass/drum bed or a mono mix, and streamed/compressed video audio often has inter-channel phase drift.
- None of the classical methods approach even the 5–6 dB vocals SDR of the smallest causal neural models.

### Gaps
- No quantitative SDR for centre-extraction or HPSS on MUSDB-style material was found in the retrieved sources.

## Key Question 6: Practical numbers — RTF/latency on phones, battery, shipping apps

### Takeaway
Measured phone numbers exist only for speech enhancement (DeepFilterNet3 RTF ≈0.15 on Android via ONNX Runtime; 8 MB) and detection (YAMNet 12 ms on Pixel 6); no phone RTF for any music separator, no published battery figure for always-on inference, and no third-party Android/iOS app does real-time on-device vocal/instrument separation of system audio — only Samsung's S26 Audio Eraser and desktop Moises Live do.

### Cited Findings
- DeepFilterNet3 on Android via ONNX Runtime: model ≈8 MB, RTF ≈0.15 (device unnamed) — [Soniqo](https://soniqo.audio/guides/denoise/android); Android JNI library (API 21+, 48 kHz mono 16-bit) and iOS SPM package (iOS 13+) — [KaleyraVideo Android](https://awesome.ecosyste.ms/projects/github.com%2Fkaleyravideo%2Fandroiddeepfilternet), [iOS](https://awesome.ecosyste.ms/projects/github.com%2Fkaleyravideo%2Fiosdeepfilternet)
- TRAMBA speech enhancement: inference under 30 ms per 512 ms window on several iPhone models (no power figure) — [arXiv 2405.01242](https://arxiv.org/pdf/2405.01242)
- Power: a near-sensor RNN accelerator paper estimates 12.55 mW continuous ≈ 4 % of a typical smartphone's 300–400 mW idle — [arXiv 1711.05734](https://arxiv.org/pdf/1711.05734); 25–50 % of inference-time power can be fixed wake/sleep overhead, which is why always-on designs use a low-power DSP — [Interspeech 2019](https://www.isca-archive.org/interspeech_2019/ramsay19_interspeech.pdf); always-on audio search argues energy per inference dominates (86,400 inferences/day at 1 Hz; ~0.6–1.5 mJ for a ~10 MFLOP net) — [arXiv 2202.05397](https://arxiv.org/abs/2202.05397)
- Samsung: on-device S26 Audio Eraser "battery consumption is slightly increased" when running continuously; no figures — [Laptop Mag](https://www.laptopmag.com/phones/android-phones/samsung-galaxy-audio-eraser-review)
- App-store survey: iOS "Vocal Remover for Karaoke" advertises real-time removal on library songs (not other apps' audio); "Master Karaoke" processes files on-device; no Android app found that removes vocals from live system audio — [App Store](https://apps.apple.com/app/id6757964697), [MWM](https://mwm.ai/apps/master-karaoke/6790194401), [SourceForge list](https://www.sourceforge.net/software/vocal-removers/android)
- Moises Live is PC/Mac only — [moises.ai](https://moises.ai/products/live/)
- Band-SCNet RTF 0.478 and Online SCNet 0.428 on a single i7-13700H thread — [Interspeech 2025](https://www.isca-archive.org/interspeech_2025/yang25d_interspeech.pdf); HS-TasNet-Small 1.83 ms per 23 ms block on 4 cores of an i7-12850HX — [L-Acoustics](https://www.l-acoustics.com/wp-content/uploads/2024/04/real_time_demixer_2024_04_19.pdf); ADI model 10.43 ms per 11.6 ms frame on a 1 GHz DSP sustaining 2.07 GMAC/s — [arXiv 2609.12201](https://arxiv.org/html/2609.12201v1)

### Inferences
- Latency budget for the brief: DeepFilterNet3 (40 ms) or GTCRN + ~10–20 ms inference + capture/playback buffering fits well inside 100–200 ms; Band-SCNet-class MSS (92 ms algorithmic) plus phone inference and buffering will sit near or above the 200 ms ceiling unless hardware-accelerated.
- Expect an always-on ~0.3–2 GMAC/s model on a phone big core to cost a few percent of battery per hour on top of media playback; no source quantifies this, so treat it as something to measure.

### Gaps
- No published RTF for Demucs/Open-Unmix/Spleeter/Band-SCNet on Snapdragon 8 Gen 2/3, Pixel Tensor, or A17/A18; no mW/battery measurement for always-on audio DNNs on a shipping phone.
- Google's technical description of Audio Magic Eraser's model and Apple's Audio Mix support page could not be fetched (search budget exhausted).
