## Key Question 1 — Interception mechanisms: PipeWire filter-chain / virtual sink + loopback / native filter API / latency & rate settings; PulseAudio and JACK equivalents

### Takeaway
On every mainstream Linux desktop (and Raspberry Pi OS Bookworm+) the sound server is PipeWire, and its built-in `libpipewire-module-filter-chain` is the canonical, zero-code way to insert a LADSPA/LV2/builtin/FFmpeg/**ONNX** processing graph as a *virtual sink* that all applications play into; the filter's playback stream then feeds the real device. PipeWire 1.6 added a native `onnx` node type to that graph (requires libonnxruntime at build time), which means a trained ONNX model can run inside the PipeWire daemon with no plugin code at all. PulseAudio's `module-ladspa-sink` / `module-null-sink` + `module-loopback` and JACK plugin hosts are the legacy equivalents.

### Cited Findings

**PipeWire filter-chain (module + graph syntax)**
- Module name is `libpipewire-module-filter-chain`; options are `node.description`, `filter.graph`, `capture.props`, `playback.props`. The filter chain "uses two streams: a capture stream feeding the graph and a playback stream sending the result onward. The session manager can then connect them to sinks and sources automatically." — [PipeWire docs: module-filter-chain](https://docs.pipewire.org/page_module_filter_chain.html)
- `filter.graph` keys: `nodes` (each with `type`, `name`, `plugin`, `label`, `config`, `control`), `links` (`<node>:<port>`), `inputs`/`outputs` (their count sets the channel count; `null` ignores a channel), plus `capture.volumes`/`playback.volumes`. Node types: `ladspa`, `lv2`, `builtin`, `sofa`, `ebur128`, `ffmpeg`, `onnx`; the last four are optional and depend on build flags. For LADSPA `plugin` is the shared-object name (PipeWire appends `.so`) and `label` selects the filter; for LV2 `plugin` is the URI from `lv2ls`. — [PipeWire docs: module-filter-chain](https://docs.pipewire.org/page_module_filter_chain.html)
- Making it a sink: `media.class = Audio/Sink` on `capture.props` makes the filter appear as a sink (apps play into it); `media.class = Audio/Source` on `playback.props` makes it a source. `node.passive = true` is set on the "other" stream so the session manager links it lazily; `audio.channels`/`audio.position` set layout. If `inputs`/`outputs` are omitted the graph is duplicated to match the stream channel count. — [PipeWire docs: module-filter-chain](https://docs.pipewire.org/page_module_filter_chain.html)
- The docs' "Dolby Surround Sink" example (condensed, documented syntax) shows a sink whose `capture.props` has `node.name = "effect_input.dolby_surround"`, `media.class = Audio/Sink`, `audio.channels = 6`, and whose `playback.props` has `node.name = "effect_output.dolby_surround"`, `node.passive = true`, `audio.channels = 2`. — [PipeWire docs: module-filter-chain](https://docs.pipewire.org/page_module_filter_chain.html)
- The docs' noise-cancelling *source* example uses `capture.props = { node.name = "capture.rnnoise_source" node.passive = true }` and `playback.props = { node.name = "rnnoise_source" media.class = Audio/Source }`. — [PipeWire 1.6 docs: module-filter-chain](https://docs.pipewire.org/1.6/page_module_filter_chain.html)
- File locations: examples use `~/.config/pipewire/filter-chain.conf.d/<name>.conf` run standalone via `pipewire -c filter-chain.conf`, or the same block placed under `pipewire.conf.d/` to run inside the main daemon. — [PipeWire docs: module-filter-chain](https://docs.pipewire.org/page_module_filter_chain.html)
- Config search order and drop-ins: `$XDG_CONFIG_HOME/pipewire/pipewire.conf`, `/etc/pipewire/pipewire.conf`, `/usr/share/pipewire/pipewire.conf`, then `/usr/share/pipewire/pipewire.conf.d/`, `/etc/pipewire/pipewire.conf.d/`, `$XDG_CONFIG_HOME/pipewire/pipewire.conf.d/` (drop-ins merged into the main config; `PIPEWIRE_CONFIG_DIR/PREFIX/NAME` env overrides). — [pipewire.conf(5)](https://docs.pipewire.org/page_man_pipewire_conf_5.html)
- Arch Wiki note: since PipeWire 1.4.10 a mono noise-suppression filter-chain may need `audio.channels = 1` and `audio.position = [ MONO ]` in **both** `capture.props` and `playback.props`. — [Arch Wiki PipeWire (2026-04 mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/PipeWire)

**PipeWire 1.6 `onnx` node type (native NN inference inside filter-chain)**
- PipeWire 1.6 (2026-02-19) "filter-graph gained FFmpeg and ONNX plugins"; 1.6 keeps API/ABI compatibility with 1.4, raised default max channels to 128, added an LDAC decoder for Bluetooth. — [Phoronix via search summary](https://phoronix.com/news/PipeWire-1.6)
- `type = onnx`: `label` is an **object** (not a string) with `filename` (path to `.onnx`), `blocksize` (samples per model call), `input-tensors` / `output-tensors` keyed by tensor name. Per-tensor keys: `dimensions`, `retain` (prepend last N samples of previous block; tensor must hold `blocksize + retain`), `data` with prefixes `port:<portname>` (creates a plugin port), `tensor:<name>` (copy from another tensor, e.g. feed output state back to input state), `param:rate`, `control:<portname>` (creates a control port). The docs' example is Silero VAD: input `dimensions = [1, 576]`, `retain = 64`, `data = "port:input"`; state `[2,1,128]` via `tensor:stateN`; `param:rate`; output `[1,1]` → `control:speech`. "The ONNX filter is optional and available only when the build includes libonnxruntime." — [PipeWire 1.6 docs: module-filter-chain](https://docs.pipewire.org/1.6/page_module_filter_chain.html)
- `type = ffmpeg`: `plugin = filtergraph`, `label` holds an FFmpeg filtergraph (e.g. `label = "[in_stereo]loudnorm=I=-18:TP=-3:LRA=4[out_stereo]"`, `inputs = [ "filter:in_stereo_0" "filter:in_stereo_1" ]`). Explicitly **not** real-time safe ("may allocate memory on the processing thread"); docs advise `node.async = true` on the streams. — [PipeWire 1.6 docs: module-filter-chain](https://docs.pipewire.org/1.6/page_module_filter_chain.html)

**Virtual sink + loopback pattern / pw-loopback**
- Arch Wiki: a null sink is created by an `adapter` object with `factory.name = support.null-audio-sink` and `media.class = Audio/Sink` in a drop-in such as `10-default-null-sink.conf`; temporary virtual devices can be made with `pw-cli` or `pactl`. — [Arch Wiki PipeWire (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/PipeWire)
- `pw-loopback [options]`: `-n/--name`, `-g/--group`, `-c/--channels`, `-m/--channel-map` (default FL,FR), `-l/--latency` (ms), `-d/--delay` (seconds, fractional ok), `-C/--capture=TARGET`, `-P/--playback=TARGET`, `-i/--capture-props=JSON`, `-o/--playback-props=JSON`. Loopback nodes can also be created by adding the loopback module to the daemon config or via `pactl load-module module-loopback`. The man page has no examples section. — [pw-loopback(1)](https://docs.pipewire.org/page_man_pw-loopback_1.html)
- `pw-cat`/`pw-play`/`pw-record [options] [FILE | -]`: `--target=VALUE` ("auto" default, `0` = don't link, or an `object.serial`/`node.name`), `--latency=VALUE[units]` (default 100 ms; bare number = samples), `--rate` (default 48000), `--channels` (default 2), `--format` (default s16), `-a/--raw`, `-P/--properties=JSON`, `--media-role` (default Music); `-` means stdin/stdout. — [pw-cat(1)](https://docs.pipewire.org/page_man_pw-cat_1.html)

**Native filter API (C) / Rust / Python**
- `pw_filter` is "designed for applications that process existing audio streams" (vs `pw_stream` for producers/consumers); Tutorial 7 builds an audio DSP filter with `pw_filter_new_simple()`, adds ports, and uses `PW_FILTER_FLAG_RT_PROCESS` so the process callback "runs in the real-time audio thread"; examples are `audio-dsp-filter.c`, `audio-dsp-src.c`. — [pw_filter struct docs](https://docs.pipewire.org/structpw__filter.html); [Tutorial 7](https://docs.pipewire.org/page_tutorial7.html)
- `pipewire-rs` crate v0.10.1 exposes modules `buffer, channel, client, constants, context, core, device, factory, keys, link, loop_, main_loop, metadata, module, node, permissions, port, properties, proxy, registry, stream, thread_loop, types` and re-exports `pw_sys` and `spa`; **no `filter` module / `Filter` type is listed**. docs.rs' build of 0.10.1 failed; canonical docs are on pages.freedesktop.org. — [pipewire-rs docs](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/index.html); [docs.rs](https://docs.rs/pipewire/latest/pipewire/)
- Real-world Rust EQ project `eqtui` drives `pw_filter` through the raw `pipewire_sys` bindings (sets `events.process = process_cb`), confirming the gap. — [eqtui src/pw/filter.rs](https://docs.rs/crate/eqtui/0.1.1-alpha.7/source/src/pw/filter.rs)

**Latency / quantum / rate settings**
- `default.clock.rate` 48000; `default.clock.allowed-rates` `[ ]` (up to 32 alternates; graph rate switches only when devices idle; off by default); `default.clock.quantum` 1024; `default.clock.min-quantum` 32; `default.clock.max-quantum` 8192; `default.clock.quantum-limit` 8192; `default.clock.quantum-floor` 4. `loop.rt-prio` default -1 (= use module-rt's priority; 0 disables RT for data loops). `node.force-quantum` is shown in a `node.rules` example (512 for `jack_simple_client`). — [pipewire.conf(5)](https://docs.pipewire.org/page_man_pipewire_conf_5.html)
- Per-app latency via env: `PIPEWIRE_LATENCY="128/48000" application`. Changing `default.clock.rate` is discouraged because quantums are not recalculated; `default.clock.allowed-rates` lets the DAC follow a stream's rate. — [Arch Wiki PipeWire (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/PipeWire)
- `PW_KEY_NODE_LATENCY` (`node.latency`) is listed among general filter-chain options, settable globally or per stream; per-node `latency` config exists for `convolver` (defaults to IR latency), `delay` (0) and `sofa` (0). The docs don't explain how these combine. — [PipeWire 1.6 docs: module-filter-chain](https://docs.pipewire.org/1.6/page_module_filter_chain.html)

**PulseAudio equivalents**
- `module-ladspa-sink` example (Arch): `pacmd load-module module-ladspa-sink sink_name=binaural master=bluez_sink.00_1F_82_28_93_51 plugin=bs2b label=bs2b control=700,4.5`; another: `pacmd load-module module-ladspa-sink sink_name=ladspa_out sink_master="$master" plugin=inv_1429 label=inv`. — [Arch Wiki PulseAudio/Examples (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/PulseAudio/Examples)
- werman's PulseAudio recipe: `module-ladspa-sink` with `sink_name=mic_raw_in sink_master=mic_denoised_out label=noise_suppressor_mono control=50,200,0,0,0` (control order: VAD Threshold %, VAD Grace ms, Retroactive VAD Grace ms, two placeholders). — [werman/noise-suppression-for-voice](https://github.com/werman/noise-suppression-for-voice)
- `pactl load-module module-null-sink sink_name=_name_ sink_properties=device.description=_description_`; `pactl load-module module-loopback source=_input_name_ sink=_sink_name_` (prints module id for `pactl unload-module`); `pactl load-module module-loopback latency_msec=1 source=gameaudio.monitor sink=$previous_default_sink`; `module-echo-cancel use_master_format=1 aec_method=webrtc aec_args="analog_gain_control=0\ digital_gain_control=1\ ..." source_master=... sink_master=... sink_name=sink_main`; `pactl set-default-sink sink_main`; `@DEFAULT_SINK@` alias; `load-module module-combine-sink sink_name=combined` + `set-default-sink combined` in `default.pa`. — [Arch Wiki PulseAudio/Examples (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/PulseAudio/Examples)

**JACK**
- PipeWire "implements the JACK API for backwards compatibility as a drop-in replacement"; `pipewire-jack` package provides this; `pipewire-jack-client` lets PipeWire run as a JACK client; routing is done with graph tools like qpwgraph. — [Arch Wiki JACK](https://wiki.archlinux.org/title/JACK_Audio_Connection_Kit); [Arch Wiki Professional audio (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/Professional_audio); [Hackster JACK/PipeWire patching](https://www.hackster.io/patrick-fitzgerald2/jack-and-pipewire-audio-patching-on-linux-245753)
- Real-time privileges: "Configuring pam_limits (e.g. by installing realtime-privileges and adding your user to the realtime group)"; CPU governor should be `performance`; `threadirqs` is default on RT kernels; `rtirq` can re-prioritise IRQ threads; `vm.swappiness = 10` in `/etc/sysctl.d/90-swappiness.conf`. — [Arch Wiki Professional audio (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/Professional_audio)

### Inferences
- Reconstructed "voice-only output sink" filter-chain (keys and values come from the DeepFilterNet shipped `deepfilter-stereo-sink.conf` and the PipeWire docs above; file text is reconstructed, not copied verbatim):
  ```
  # ~/.config/pipewire/pipewire.conf.d/99-voice-only-sink.conf
  context.modules = [
    { name = libpipewire-module-filter-chain
      args = {
        node.description = "DeepFilter Noise Canceling Sink"
        media.name       = "DeepFilter Noise Canceling Sink"
        filter.graph = {
          nodes = [
            { type = ladspa
              name = "DeepFilter Stereo"
              plugin = /usr/lib/ladspa/libdeep_filter_ladspa.so   # absolute path if installed locally
              label = deep_filter_stereo
              control = { "Attenuation Limit (dB)" = 100 }        # 100 = no limit
            }
          ]
        }
        audio.rate = 48000
        audio.channels = 2
        audio.position = [ FL FR ]
        capture.props  = { node.name = "deep_filter_stereo_input"  media.class = Audio/Sink }
        playback.props = { node.name = "deep_filter_stereo_output" node.passive = true }
      }
    }
  ]
  ```
  Then `wpctl set-default <id-of-deep_filter_stereo_input>` (or `pactl set-default-sink deep_filter_stereo_input`) makes every application play through it; the `playback.props` stream, having no `target.object`, is linked by WirePlumber to the current real output.
- The same block with `type = onnx` (PipeWire ≥ 1.6) would let a custom enhancement/separation ONNX model run in-daemon, but see Gap below about audio-output tensors.
- Because PipeWire's JACK layer is a drop-in, any JACK plugin host (Carla, jalv) that loads an LV2/LADSPA voice filter is also a valid system-wide hook once the host's ports are wired between a virtual sink's monitor and the hardware sink; this is more fragile than filter-chain (extra process, manual port wiring) and I found no project doing it for ML voice isolation.
- For a Python daemon, the lowest-friction system-wide route is: null/virtual sink as default → `pw-record --target <sink>.monitor --raw --format f32 --rate 48000 -` → Python STFT+model → `pw-play --raw ... --target <hardware sink> -`. pw-cat's default node latency is 100 ms each way, so the explicit `--latency` flag matters.

### Gaps
- The PipeWire `onnx` docs example only routes a model *output* to a control port (VAD probability). Whether an **output tensor** can be mapped with `data = "port:<name>"` to produce audio (needed for enhancement/separation) is not explicit in the page text I could read; needs a test or reading `module-filter-chain/onnx.c`.
- The PipeWire GitLab wiki ("Filter-Chain", "Virtual-Devices", "Config-PipeWire") and the live Arch Wiki were Anubis-blocked; I used docs.pipewire.org and an April-2026 Arch mirror instead.
- I did not find official documentation (only the man page option list) for `pw-loopback` creating a `media.class=Audio/Sink` virtual sink via `--capture-props`; the pattern is widely used but I have no verbatim doc example.
- No source gave a measured end-to-end latency of a filter-chain sink (quantum + plugin latency); only plugin-internal latencies are documented (see KQ2).
- Carla/jalv specifics (`carla-single`, `jalv.gtk <uri>`) were not on the Arch mirror page I could fetch.

## Key Question 2 — Existing open-source projects doing ML speech enhancement system-wide on Linux; how each hooks in; can they process OUTPUT (speakers), not just mic?

### Takeaway
Yes, existence proofs exist: DeepFilterNet ships a stereo *sink* filter-chain config ("creates a virtual output that suppresses noise from applications, leaving mainly speech"), NoiseTorch has an output "Filtered Headphones" mode, EasyEffects runs DeepFilterNet/DPDFNet/RNNoise/Speex on PipeWire and can load the DPDFNet plugin on playback audio, and HushMic packages DPDFNet as a LADSPA plugin driven by a self-written filter-chain. All of these are *speech enhancement* (they treat music as noise); none is a music-source-separation model.

### Cited Findings

**DeepFilterNet (Rikorose)**
- Repo provides a LADSPA plugin "with PipeWire filter-chain integration for real-time noise reduction"; `deep-filter` binary supports only 48 kHz WAV; models DeepFilterNet, DeepFilterNet2 (default), DeepFilterNet3; Rust workspace crates `libDF`, `pyDF`, `pyDF-data`, `ladspa`, `df-demo`. 1,603 commits; Releases section shows no date. — [DeepFilterNet README](https://github.com/Rikorose/DeepFilterNet)
- LADSPA README: "The minimum latency is 20 ms (STFT processing)" plus host latency; the model has no lookahead; build with `cargo build --release -p deep-filter-ladspa` → `target/release/libdeep_filter_ladspa*` (or download from Releases); configs `deepfilter-mono-source.conf` (virtual mic) and `deepfilter-stereo-sink.conf` ("creates a virtual output that suppresses noise from applications, leaving mainly speech"); run with `pipewire -c filter-chain.conf`; debug with `RUST_LOG=DEBUG`. — [DeepFilterNet ladspa/README.md](https://github.com/Rikorose/DeepFilterNet/blob/main/ladspa/README.md)
- `deepfilter-stereo-sink.conf` contents: module `libpipewire-module-filter-chain`; `node.description`/`media.name` "DeepFilter Noise Canceling Sink"; node `type = ladspa`, `name = "DeepFilter Stereo"`, `plugin = /usr/lib/ladspa/libdeep_filter_ladspa.so`, `label = deep_filter_stereo`, `control = { "Attenuation Limit (dB)" = 100 }` (100 = no limit); `audio.rate = 48000`, `audio.channels = 2`, `audio.position = [FL FR]`; `capture.props = { node.name = deep_filter_stereo_input, media.class = Audio/Sink }`; `playback.props = { node.name = deep_filter_stereo_output, node.passive = true }`. — [deepfilter-stereo-sink.conf (raw)](https://raw.githubusercontent.com/Rikorose/DeepFilterNet/main/ladspa/filter-chain-configs/deepfilter-stereo-sink.conf)
- DeepFilterNet paper: real-time factor 0.19 on a single-threaded notebook CPU. — [arXiv 2110.05588](https://arxiv.org/abs/2110.05588v1)
- EasyEffects "Deep Noise Remover" uses DeepFilterNet; docs recommend attenuation ~70–80 dB and "Maximum DF Processing Threshold" ~20 dB. — [EasyEffects docs: deepfilternet](https://wwmm.github.io/easyeffects/deepfilternet.html) (via search snippet; direct fetch 404'd)
- Fedora workaround: copy `libdeep_filter_ladspa.so` into the system LADSPA dir and restart EasyEffects. — [gist](https://gist.github.com/Memoraike/e0c35b5fb16228b169775cc7af34b884/)

**werman/noise-suppression-for-voice (RNNoise)**
- Formats: VST2, VST3, LV2, LADSPA, AU/AUv3 (macOS). "works with one or more channels, 16 bit, 48000 Hz audio input"; "Do NOT use any other sample rates, use ONLY 48000 Hz." Controls: "VAD Threshold (%)" (recommend 85–95), "VAD Grace Period (ms)", "Retroactive VAD Grace (ms)" ("This introduces latency!"). PipeWire example: `ladspa` node with `plugin = /path/to/librnnoise_ladspa.so`, `label = noise_suppressor_mono`, `audio.rate = 48000` on both sides, playback `media.class = Audio/Source`, saved as `~/.config/pipewire/pipewire.conf.d/99-input-denoising.conf`. README does not address output/sink use. — [werman README](https://github.com/werman/noise-suppression-for-voice)
- Arch Wiki packages this as `noise-suppression-for-voice`; mono rule since PipeWire 1.4.10 (see KQ1). — [Arch Wiki PipeWire (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/PipeWire)

**NoiseTorch**
- "Noise Supression Application for PulseAudio or Pipewire"; creates "Filtered Microphone"; "Output filtering works the same way" — route apps to "Filtered Headphones"; "inherent latency introduced by noise supression is 10ms"; output filtering "adds roughly 100ms of latency with PulseAudio"; latest version visible is v0.12.2; after a suspected update-server breach, updates ship only via GitHub Releases (audit found no malicious code). README has no CLI flag section (so `-o`/`-i` flags could not be confirmed from it). — [NoiseTorch README](https://github.com/noisetorch/NoiseTorch); [raw README](https://raw.githubusercontent.com/noisetorch/NoiseTorch/master/README.md)

**EasyEffects**

**HushMic / DPDFNet (new, 2025–26)**
- HushMic: Linux real-time mic noise suppression; `hushmic` writes a PipeWire `module-filter-chain` config and runs it as a child process ("PipeWire owns the real-time scheduling, so no setcap is needed"); watchdog recreates the virtual mic after PipeWire restart/suspend; crate `dpdfnet-ladspa` → `libdpdfnet_ladspa.so`; "Processing adds 80 ms of latency" (plus PipeWire buffering; "On PipeWire 1.6 and later, apps like OBS can compensate"); 48 kHz mono; native engine uses < ½ the CPU of ONNX Runtime on AVX2/FMA, ~¼–⅓ on AVX-VNNI; "quality" and "light" models; `hushmic --headless`; `hushmic config set autostart true`; systemd user unit in docs/headless.md. README describes mic only; "EasyEffects can load HushMic's plugin on playback audio, but that is an EasyEffects feature." — [HushMic README](https://raw.githubusercontent.com/Fovty/HushMic/main/README.md); [AUR hushmic-bin](https://aur.archlinux.org/packages/hushmic-bin)
- DPDFNet (Ceva, Apache-2.0): causal single-channel speech enhancement adding dual-path RNN blocks to the DeepFilterNet2 encoder. — [arXiv 2512.16420](https://arxiv.org/abs/2512.16420v1); [HF Ceva-IP/DPDFNet](https://huggingface.co/Ceva-IP/DPDFNet/blob/main/README.md)
- sherpa-onnx (k2-fsa) supports speech enhancement with `gtcrn_simple` and DPDFNet (8/16/48 kHz variants, offline **and streaming** Python/C APIs), and claims support for Raspberry Pi, RK NPU, Axera NPU, RISC-V etc. — [sherpa-onnx speech enhancement docs](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/index.html); [sherpa-onnx README](https://github.com/k2-fsa/sherpa-onnx)

**Music-separation-as-a-stream on Linux (existence proofs, not system-wide daemons)**
- GStreamer 1.28.0 (released 27 Jan 2026) added a Rust `demucs` element ("new audio source separation element based on demucs"; "useful to separate speech from background audio before running speech to text transcription"); shipped by Cerbero on all platforms except Windows ARM64; 1.28.1 added a whisper STT element. — [GStreamer 1.28 release notes](https://gstreamer.freedesktop.org/releases/1.28/)
- Centricular devlog: element runs the Python/PyTorch demucs either in-process (pyo3 embedded interpreter) or via a WebSocket Python service (local or remote); model, chunk size and overlap configurable ("Smaller chunks reduce latency but lower quality"); CPU "several times real-time", ~8× on the author's machine; karaoke pipeline uses `demucs name=demucs model-name=htdemucs`, `demucs.src_vocals ! queue ! audioamplify amplification=-1 ! mixer.sink_0` against a **9-second** queue on the dry branch. Live sources are not discussed. — [Centricular devlog 2025-12](https://centricular.com/devlog/2025-12/demucs/)
- `python-audio-separator-live` (MDX-NET ONNX / Mel-Band RoFormer): ~1.7 s end-to-end latency on GPU (1.4 s window fill + inference + one frame); blocksize 4410 @44.1 kHz, 16-frame window, 12-frame initial wait; RTX 5080 inference 0.10 s/window (RoFormer), 0.18 s (MDX-NET); CPU "roughly 10x slower"; `--stem vocals`; capture via VB-Cable on Windows ("Loopback capture is not supported by sounddevice"); no Linux support stated. — [nnyj/python-audio-separator-live](https://github.com/nnyj/python-audio-separator-live)
- Demucs README points to a realtime Demucs model in Neutone's free VST/AU plugin; Neutone 1.4 lists Windows/macOS only. — [facebookresearch/demucs](https://github.com/facebookresearch/demucs); [Sonicstate Neutone 1.4](https://sonicstate.com/news/2023/07/06/neutone-updated-to-v14-)

### Inferences
- The *only* turnkey "all app audio → voice-only → speakers" path with upstream-shipped config is DeepFilterNet's `deepfilter-stereo-sink.conf` (20 ms plugin latency + PipeWire quantum). HushMic/DPDFNet is the newer/stronger denoiser but ships as a mic tool; its LADSPA plugin can be dropped into the same stereo-sink filter-chain by changing `plugin`/`label` (label not stated in README — check `ladspa -l` / `listplugins`).
- EasyEffects is GUI-centric but works headlessly via `--gapplication-service` + a systemd user unit; it is the only project that already exposes the DPDFNet/DeepFilterNet denoisers on the **output** chain with a UI for thresholds.
- Speech-enhancement models suppress music as "noise" only to the extent their training noise sets included music; sustained tonal/harmonic instruments (and singing) overlap speech features and will partly leak through — none of the projects above claims instrument removal.
- GStreamer `demucs` is the only packaged, Linux-native way to run a true music-separation model as a streaming element; with `pipewiresrc`/`pipewiresink` it could in principle sit between a null sink's monitor and the hardware sink, but the author's example buffers 9 s and does not discuss live use.

- NoiseTorch CLI flags (`-i/-o/-s/-u/-t`) could not be verified from the README text; whether NoiseTorch still works on current PipeWire (it loads PulseAudio LADSPA modules through pipewire-pulse) is unverified.

## Key Question 3 — Writing your own real-time NN filter: (a) LADSPA/LV2/CLAP plugin embedding ONNX/TFLite loaded by filter-chain, (b) standalone daemon (Rust/Python), (c) GStreamer nnstreamer/pytorch; latency / CPU / robustness comparison

### Takeaway
The lowest-latency, most robust option is a native plugin (or, on PipeWire ≥ 1.6, the built-in `onnx` node) running inside the PipeWire filter-chain, because PipeWire owns the RT thread, the sink identity, and reconnection; a standalone Rust/Python daemon costs two extra stream hops (≈100 ms default each with pw-cat unless tuned) and must handle reconnection itself; GStreamer gives you Demucs today but with second-scale chunk buffering and a non-RT process model. DeepFilterNet (Rust, 20 ms) and HushMic (Rust `dpdfnet-ladspa`, 80 ms, native engine < ½ the CPU of ORT) are the working templates for option (a).

### Cited Findings
- Option (a) templates: DeepFilterNet's `ladspa` crate (Rust, `cargo build --release -p deep-filter-ladspa`, 20 ms minimum latency from STFT, no-lookahead model) — [DeepFilterNet ladspa README](https://github.com/Rikorose/DeepFilterNet/blob/main/ladspa/README.md); HushMic's `dpdfnet-ladspa` crate (80 ms added latency; custom native inference engine using < ½ the CPU of ONNX Runtime on AVX2/FMA, ~¼–⅓ on AVX-VNNI; PipeWire owns RT scheduling so no `setcap`) — [HushMic README](https://raw.githubusercontent.com/Fovty/HushMic/main/README.md); werman's RNNoise plugin (LADSPA/LV2/VST2/VST3) — [werman README](https://github.com/werman/noise-suppression-for-voice).
- Option (a′) no-plugin: PipeWire 1.6 `type = onnx` node — model file, `blocksize`, `retain` overlap, `tensor:` state feedback for stateful/causal models, `param:rate`; requires PipeWire built with libonnxruntime. — [PipeWire 1.6 docs: module-filter-chain](https://docs.pipewire.org/1.6/page_module_filter_chain.html)
- Option (a″) FFmpeg filtergraph node exists but is "not real-time safe" (allocates on the processing thread); docs advise `node.async = true`. — [PipeWire 1.6 docs: module-filter-chain](https://docs.pipewire.org/1.6/page_module_filter_chain.html)
- Option (b) C API: `pw_filter` with `PW_FILTER_FLAG_RT_PROCESS` runs `process` in the RT audio thread; examples `audio-dsp-filter.c`. — [Tutorial 7](https://docs.pipewire.org/page_tutorial7.html); [pw_filter](https://docs.pipewire.org/structpw__filter.html)
- Option (b) Rust: `pipewire` crate 0.10.1 has `stream` but no `Filter` binding; eqtui uses raw `pipewire_sys` for `pw_filter`. — [pipewire-rs docs](https://pipewire.pages.freedesktop.org/pipewire-rs/pipewire/index.html); [eqtui filter.rs](https://docs.rs/crate/eqtui/0.1.1-alpha.7/source/src/pw/filter.rs)
- Option (b) Python/pipe: `pw-record`/`pw-play` with `--raw --format --rate --channels --target --latency` and `-` for stdin/stdout; default node latency 100 ms. — [pw-cat(1)](https://docs.pipewire.org/page_man_pw-cat_1.html). `python-audio-separator-live` shows the sounddevice approach but notes sounddevice has no loopback capture (so a virtual cable / monitor source is required). — [python-audio-separator-live](https://github.com/nnyj/python-audio-separator-live)
- Option (c) GStreamer: `demucs` element (1.28.0; PyTorch via pyo3 or WebSocket service; CPU ~8× real-time; 9 s dry-branch queue in the example) — [Centricular](https://centricular.com/devlog/2025-12/demucs/); [GStreamer 1.28 notes](https://gstreamer.freedesktop.org/releases/1.28/). GStreamer 1.28 also lists `onnx` (Verisilicon provider), a LiteRT inference element, and `tensordecodebin`. — [GStreamer 1.28 notes](https://gstreamer.freedesktop.org/releases/1.28/)
- Option (c) nnstreamer: `tensor_filter` "connects gstreamer data stream with neural network frameworks (NNFW) such as Tensorflow or Caffe"; you "specify neural network framework, model path, and model meta information"; the two-tensor example feeds an audio source through `tensor_filter` with a custom speech-command model library; a vendor audio-classification pipeline uses `pulsesrc` → converter → tensors → model. — [nnstreamer tensor_filter](https://nnstreamer.github.io/gst/nnstreamer/tensor_filter/README.html); [nnstreamer two-tensor example](https://nnstreamer.github.io/nnstreamer-example/native/example_two_tensor_stream/README.html); [Qualcomm LiteRT audio classification](https://docs.qualcomm.com/bundle/publicresource/80-70023-50/topics/audio-classification-with-litert.md?product=1601111740013886)
- RT scheduling for any in-daemon option: `libpipewire-module-rt` (`nice.level`, `rt.prio`, `rt.time.soft/hard`, `rlimits.enabled`, `rtportal.enabled`, `rtkit.enabled`, `uclamp.min/max`; needs `RLIMIT_RTPRIO ≥ rt.prio`, else falls back to the Realtime portal or RTKit over D-Bus; override via `module.rt.args` in `~/.config/pipewire/pipewire.conf.d/my-rt-args.conf`). — [module-rt docs](https://docs.pipewire.org/page_module_rt.html)

### Inferences
- Comparison (derived from the cited numbers):
  | Option | Added latency | CPU | Robustness | Notes |
  |---|---|---|---|---|
  | (a) LADSPA/LV2 plugin in filter-chain (Rust/C + ORT/tract/custom) | plugin algorithmic latency only (20 ms DFN, 80 ms DPDFNet) + quantum (1024/48 k ≈ 21 ms default; tunable to 256–512) | one RT thread inside pipewire; HushMic shows a hand-written engine beats ORT by 2–4× | highest: PipeWire restarts/relinks it; sink persists across device hot-plug | must be RT-safe (no allocs/locks in `run()`); LADSPA has no latency-report port, LV2 does |
  | (a′) PipeWire `onnx` node | same as above; `blocksize` sets frame hop | ORT CPU EP inside daemon | same as (a) | needs distro PipeWire built with onnxruntime; stateful models via `tensor:` feedback |
  | (b) standalone daemon (Rust sys bindings / Python via pw-cat pipes or sounddevice) | ≥ 2 extra stream hops; pw-cat default 100 ms each unless `--latency` set | process can use GPU/NPU freely (CUDA/OpenVINO/RKNN) | must watch for PipeWire restart and re-create nodes (HushMic implements such a watchdog) | best when the model needs a GPU or a large PyTorch runtime |
  | (c) GStreamer demucs / nnstreamer | seconds (chunked Demucs; 9 s example queue) | PyTorch, ~8× RT on CPU per author | GStreamer pipelines are not RT-safe; use `pipewiresrc`/`pipewiresink` with large queues | only option today with a real music-separation model |
- For an embedded appliance, option (a)/(a′) with an int8/fp16 ONNX or a hand-rolled engine on the CPU is the practical path; the NPU routes (KQ4) require ahead-of-time model conversion and are better served by option (b).

### Gaps
- No source measured end-to-end latency of a filter-chain LADSPA sink on a desktop (quantum + plugin); only component figures exist.
- I found no public LV2/CLAP plugin that embeds ONNX Runtime generically for arbitrary audio models (neural-amp-modeler-style template for enhancement) — the nearest are the model-specific DeepFilterNet and dpdfnet-ladspa crates.
- Python bindings for `pw_filter` (a "python-pipewire" filter node) were not found; nothing beyond pw-cat piping and sounddevice.
- nnstreamer: no complete microphone→`tensor_filter`→audio-out example with exact caps was found; also no PipeWire-native source element example.

## Key Question 4 — Headless/always-on: systemd user service, hot-plug (Bluetooth/HDMI) survival, WirePlumber routing rules, RT scheduling, GPU/NPU inference on desktop and Raspberry Pi 5 / RK3588 / Hailo-8, Bluetooth A2DP-sink appliance

### Takeaway
PipeWire/WirePlumber already run as socket-activated systemd **user** units, so the filter-chain is "always on" simply by living in `pipewire.conf.d/` (or as its own `pipewire -c` unit ordered after `pipewire.service`); WirePlumber's default-sink following is deliberately *not* applied to filter streams, so hot-plug behaviour must be handled by leaving the filter's playback stream untargeted (so it links to whatever the session manager picks) or by WirePlumber priority rules. On hardware: desktop ONNX Runtime covers CUDA/TensorRT, OpenVINO (CPU/GPU/NPU), ROCm (now deprecated in favour of MIGraphX); Raspberry Pi 5 + AI HAT+ (Hailo-8L/8) and RK3588 (RKNN) are proven for ASR/TTS but I found no proof of a speech-enhancement or separation model deployed on either NPU; a Pi as Bluetooth A2DP sink with PipeWire/WirePlumber is documented by Collabora.

### Cited Findings

**systemd / service model**
- PipeWire is "managed by systemd/User with socket activation"; enable `pipewire.service`, `pipewire-pulse.service`, `wireplumber.service` as user units. — [Arch Wiki PipeWire (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/PipeWire)
- WirePlumber status/logs: `systemctl --user status wireplumber`, `journalctl --user -u wireplumber`. — [WirePlumber getting started](https://pipewire.pages.freedesktop.org/wireplumber/_sources/daemon/getting_started.rst.txt)
- Pitfall: a systemd service does not inherit the user's env, so `pactl`/`wpctl` calls from units need e.g. `XDG_RUNTIME_DIR` set explicitly. — [tnsp.org forum notes](https://tnsp.org/~ccr/files/wireplumber-pipewire-problems.html)
- Community EasyEffects unit: `ExecStart=/usr/bin/easyeffects --gapplication-service` ordered after `pipewire.service` and `wireplumber.service`. — [tiyn wiki](https://git.tiyn.eu/tiyn/wiki/commit/32e6023f600e32479fb11da55d8c3c19898d10da)
- HushMic: filter-chain spawned as a child process with a watchdog that recreates the node after PipeWire restart/suspend; `--headless` mode; systemd user unit documented. — [HushMic README](https://raw.githubusercontent.com/Fovty/HushMic/main/README.md)
- Headless Pi: on Raspberry Pi OS Lite the auto-logged-in user starts PipeWire/WirePlumber (enable "Console Autologin" in `raspi-config` if needed); Collabora's BlueZ agent runs as a systemd user unit in `~/.config/systemd/user/`, enabled with `systemctl --user enable speaker-agent.service`. — [Collabora Pi Bluetooth speaker guide](https://www.collabora.com/news-and-blog/blog/2022/09/02/using-a-raspberry-pi-as-a-bluetooth-speaker-with-pipewire-wireplumber)

**Hot-plug / routing rules (WirePlumber)**
- `linking.follow-default-target` (default `true`): "the stream will be moved to the new 'default' target" — but the logic "is only applied on client (i.e. application) streams and *not* on filters." `linking.allow-moving-streams` (true); `stream.restore-default-targets` (true); `stream.restore-target` (true); `device.restore-profile` (true); `bluetooth.autoswitch-to-headset-profile` (true: switches to HSP/HFP when an app records). — [WirePlumber settings](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/settings.html)
- WirePlumber 0.4.10 release note: "filter-like streams (filter-chain and such) no longer follow the default sink when it changes, like in PulseAudio"; 0.4.3: "Policy now respects the `node.link-group` property, which fixes issues with filter-chain and other virtual sources". — [WirePlumber releases (mirror, stops at 0.4.10)](https://darix.pages.freedesktop.org/wireplumber/releases.html)
- Open issue: a filter stream whose `target.object` node is missing falls back to the default device; `node.dont-reconnect` expected to prevent this but reported broken on `next`. — [wireplumber#524](https://gitlab.freedesktop.org/pipewire/wireplumber/-/issues/524)
- Open issue: WirePlumber event processing can hang at startup "if a virtual sink is already loaded, configured and it's the default sink when wireplumber starts" (filter-chain in `~/.config/pipewire/filter-chain.conf.d/`, made default). — [wireplumber#527](https://gitlab.freedesktop.org/pipewire/wireplumber/-/issues/527)
- Default-node priority: highest `priority.session` wins only when no user selection is saved; `wpctl set-default` persists and outranks priorities; `wpctl clear-default` resets; rules belong to the creating monitor (`monitor.alsa.rules`, `monitor.bluez.rules`, e.g. `priority.session = 900` for `bluez_output`); ties break by discovery order. — [WirePlumber priorities](https://pipewire.pages.freedesktop.org/wireplumber/daemon/configuration/priorities.html)

**Real-time scheduling / CPU**
- `libpipewire-module-rt` options and the RLIMIT_RTPRIO → portal → RTKit fallback chain; `loop.rt-prio` default -1. — [module-rt](https://docs.pipewire.org/page_module_rt.html); [pipewire.conf(5)](https://docs.pipewire.org/page_man_pipewire_conf_5.html)
- Pro-audio tuning: `realtime-privileges` + `realtime` group; `performance` governor; `threadirqs`/`rtirq`; swappiness 10. — [Arch Wiki Professional audio (mirror)](https://wikipedia.jakami.de/content/archlinux_en_all_maxi_2026-04/Professional_audio)

**Desktop GPU/NPU inference**
- ONNX Runtime EP catalogue: CUDA, TensorRT, DirectML, OpenVINO, MIGraphX (ROCm EP marked **deprecated**), QNN, XNNPACK, Arm NN (preview), ACL (preview), CoreML (preview), CANN (preview), Vitis-AI (preview); OS support not stated on the index page. — [ORT execution providers](https://onnxruntime.ai/docs/execution-providers/)
- OpenVINO EP: devices CPU/GPU/**NPU** (`device_type = NPU`, `AUTO:GPU,NPU,CPU`, `HETERO:`, `MULTI:`); Linux setup via `setupvars.sh`, wheels for Ubuntu; ORT 1.24.1 ↔ OpenVINO 2025.4.1; NPU is FP16-only, needs static/bounded shapes (`reshape_input`, `disable_dynamic_shapes`), unsupported ops fall back to CPU; built-in EP deprecated in favour of `pip install onnxruntime-ep-openvino`. — [ORT OpenVINO EP](https://onnxruntime.ai/docs/execution-providers/OpenVINO-ExecutionProvider.html)

**Raspberry Pi 5 / Hailo / RK3588**
- AI HAT+: Hailo-8L (13 TOPS) or Hailo-8 (26 TOPS); Pi docs say Hailo's examples and custom models can be used for speech-to-text, translation, scene analysis (speech enhancement not named). — [Raspberry Pi AI HAT+ docs](https://www.raspberrypi.com/documentation/accessories/ai-hat-plus.html)
- Hailo community: Whisper on Pi 5 with encoder on Hailo-8L and decoder on CPU gave live captions with ~250 ms refresh; an ONNX audio model with leading 1-D convolutions failed to parse in the Hailo compiler (unresolved). — [Hailo community: real-time ASR](https://community.hailo.ai/t/real-time-asr-on-raspberry-pi-hailo8l-with-whisper/17936); [Hailo community: voice transcription thread](https://community.hailo.ai/t/using-rpi5-hailo8-ai-hat-26-tops-for-local-voice-transcription/16092)
- RK3588: workflow PyTorch → ONNX → RKNN → NPU runtime; Piper TTS on the RK3588 NPU reached RTF ≈ 0.15 via RKNN. — [tinycomputers RK3588 NPU](https://tinycomputers.io/posts/rockchip-rk3588-npu-benchmarks.html); [clehaxze Piper on RK3588](https://clehaxze.tw/gemlog/2023/12-24-accelerating-piper-text-to-speech-on-the-rk3588-npu.gmi)
- sherpa-onnx lists Raspberry Pi, RK NPU, Axera NPU, Ascend NPU among supported targets and includes speech enhancement (GTCRN, DPDFNet) and source separation. — [sherpa-onnx README](https://github.com/k2-fsa/sherpa-onnx); [sherpa-onnx speech enhancement](https://k2-fsa.github.io/sherpa/onnx/speech-enhancement/index.html)
- A 2025/26 paper claims real-time music source separation on a low-power audio DSP (arXiv id "2609.12201" — flagged: the id prefix is unusual; verify). — [arXiv 2609.12201](https://arxiv.org/pdf/2609.12201)

- 2026 guide: Raspberry Pi OS Bookworm ships PipeWire; install `pipewire-pulse wireplumber libspa-0.2-bluetooth`; onboard BT shares the WiFi antenna (audio glitches reported, citing the Raspberry Pi Audio Receiver project). — [fast.io OpenClaw Pi receiver (vendor blog)](https://www.fast.io/resources/openclaw-raspberry-pi-bluetooth-audio-receiver-speaker-agent.md)
- Forum reports: most BT modules handle one active A2DP connection at a time; the Pi's analog jack DAC is poor, prefer USB audio. — [hudiy.eu thread](https://hudiy.eu/community/viewtopic.php?t=259)

### Inferences
- Proposed always-on layout (desktop or Pi): (1) `~/.config/pipewire/pipewire.conf.d/99-voice-only-sink.conf` with the filter-chain sink (loaded by `pipewire.service` itself — no extra unit); (2) a one-shot user unit after `wireplumber.service` running `wpctl set-default $(pw-cli ls Node | ... deep_filter_stereo_input)` (or rely on `stream.restore-default-targets` after setting it once); (3) headless boxes: `loginctl enable-linger <user>` so user units start without a login session (not stated in the Collabora guide, which relies on console autologin instead — treat as my inference). Alternative for a GUI-less appliance: run `pipewire -c filter-chain.conf` as its own user unit (documented standalone mode) so a plugin crash does not take the sound server down.
- Hot-plug: because filter streams do not follow the default sink, the safest pattern is to leave `playback.props` **without** `target.object` so WirePlumber links it to whatever the current best device is, and let hardware-device priorities (`priority.session` rules for bluez/ALSA/HDMI) decide; combine with `device.restore-profile` for BT. Test against wireplumber#527 (filter sink saved as default at boot) on your WirePlumber version.
- Embedded "appliance in a box": Pi 5 (CPU) is sufficient for DeepFilterNet-class models given RTF 0.19 on a single notebook core, but the NPU routes (Hailo/RKNN) need operator-compatible graphs (static shapes, no leading 1-D conv issues) and have no published speech-enhancement deployment I could find; prefer CPU int8 via ORT/sherpa-onnx or HushMic's native engine, and reserve the NPU for a future separation model.
- Desktop GPU: use option (b) (standalone daemon) when the model needs CUDA/OpenVINO; the PipeWire-internal `onnx` node will use whatever EP the distro's libonnxruntime was built with (unverified — see gap).

### Gaps
- No documentation found on which ONNX Runtime execution provider the PipeWire `onnx` filter uses (CPU only vs configurable EP).
- WirePlumber's current (0.5.x/1.x-era) release page was 404 at the canonical URL; the mirror stops at 0.4.10, so I cannot cite post-0.4.10 changes to filter-stream policy.
- No proof found of DeepFilterNet/DPDFNet/GTCRN compiled to Hailo HEF or RKNN; no RTF figures for speech enhancement on Pi 5 CPU.
- `loginctl enable-linger` for headless PipeWire user sessions, PipeWire "system mode", and HDMI hot-plug specifics were not covered by any fetched source.
- `pw-top` usage for measuring per-node CPU/quantum was not researched (out of budget).

## Key Question 5 — Can any of this separate SINGING voice from instruments in real time (vs speech enhancement that removes music as noise)?

### Takeaway
Real-time singing/instrument separation is an active research area with sub-100 ms models (HS-TasNet 23 ms, Band-SCNet 92 ms, RT-STT), but as of Nov 2026 I found **no Linux system-wide daemon or PipeWire/JACK plugin** that runs one; the deployable Linux options are chunked Demucs in GStreamer (seconds of latency) or Windows-oriented ~1.7 s tools. Speech-enhancement plugins (DeepFilterNet/DPDFNet/RNNoise) are what actually exists system-wide, and they keep *speech* while attenuating music, not singing.

### Cited Findings
- HS-TasNet (L-Acoustics, ICASSP 2024): hybrid spectrogram/waveform model "inspired by the Hybrid Demucs architecture" separating vocals/drums/bass/other at 23 ms latency (1024-sample frame @ 44.1 kHz); SDR 4.65 on MUSDB (5.55 with extra data); target "hearing aids, remixing audio streams and live shows"; offline models adapted to RT caused artifacts; no code/weights link on the abstract page. — [arXiv 2402.17701](https://arxiv.org/abs/2402.17701); [L-Acoustics PDF](https://www.l-acoustics.com/wp-content/uploads/2024/04/real_time_demixer_2024_04_19.pdf)
- Band-SCNet (Interspeech 2025): causal lightweight model, SDR 7.79 dB, larger variant at 92 ms latency. — [ISCA archive](https://www.isca-archive.org/interspeech_2025/yang25d_interspeech.pdf)
- RT-STT (Nov 2025): single-path TFC-TDF UNet based on DTTNet; claims better performance than SOTA real-time models with far fewer parameters and shorter inference; studies quantization; no numbers or code link on the abstract page. — [arXiv 2511.13146](https://arxiv.org/abs/2511.13146)
- "Real-Time Music Source Separation on a Low-Power Audio DSP" claims no prior published real-time separator runs on its target hardware (arXiv id flagged as unusual; verify). — [arXiv 2609.12201](https://arxiv.org/pdf/2609.12201)
- GStreamer 1.28 `demucs` element: PyTorch Demucs, chunk size/overlap trade latency vs quality, ~8× real-time on CPU, example uses a 9 s queue; vocals pad `src_vocals`; stated use "separate speech from background audio before running speech to text". — [Centricular](https://centricular.com/devlog/2025-12/demucs/); [GStreamer 1.28](https://gstreamer.freedesktop.org/releases/1.28/)
- `python-audio-separator-live`: Mel-Band RoFormer / MDX-NET, ~1.7 s latency on GPU, "Window sizes under about 1.5s degrade quality", `--stem vocals`, Windows/VB-Cable workflow. — [nnyj/python-audio-separator-live](https://github.com/nnyj/python-audio-separator-live)

- Speech enhancement side: DeepFilterNet's stereo sink "suppresses noise from applications, leaving mainly speech"; DPDFNet is "causal, single-channel speech enhancement … for real-time noise suppression"; RNNoise plugin gates on a voice-activity probability ("if probability of sound being a voice is lower than this threshold - it will be silenced"). — [DeepFilterNet ladspa README](https://github.com/Rikorose/DeepFilterNet/blob/main/ladspa/README.md); [HushMic README](https://raw.githubusercontent.com/Fovty/HushMic/main/README.md); [werman README](https://github.com/werman/noise-suppression-for-voice)
- sherpa-onnx advertises "source separation" (alongside speech enhancement) with Pi/RK NPU targets. — [sherpa-onnx README](https://github.com/k2-fsa/sherpa-onnx)

### Inferences
- For a "keep human voice, drop instruments" product on Linux today there are two tiers: (1) ship now with speech-enhancement plugins in a filter-chain sink (20–80 ms, CPU-only, but singing is treated as speech-like and partially kept, and harmonic instruments may leak); (2) build a custom real-time separator (HS-TasNet/Band-SCNet-class, 23–92 ms) exported to ONNX and run via the PipeWire `onnx` node or a Rust LADSPA plugin — the plumbing exists, but the model weights do not appear to be public, so training/distilling is required.
- GStreamer `demucs` + `pipewiresrc`/`pipewiresink` is the quickest Linux proof-of-concept for *true* instrument removal (vocals-only or dialogue-only from `src_vocals`), at the cost of multi-second latency — acceptable for passive listening (podcasts, lectures, video with delayed display) but not for games/calls.
- Whether singing counts as "voice to keep" is a product decision: speech-enhancement models will largely keep it; music-separation models put it in the `vocals` stem, so an "instrument mute" that keeps both speech and singing maps to "vocals stem only", while "speech only" needs an additional speech/singing discriminator (not researched).

### Gaps
- No open-source real-time (< 100 ms) music-separation model with public weights was confirmed; HS-TasNet, Band-SCNet, RT-STT code availability unverified from abstract pages.
- No GitHub project found for "pipewire demucs", "jack vocal isolation", "open-unmix realtime", or "torchaudio streaming separation"; searches returned only offline Demucs guides.
- sherpa-onnx's "source separation" models (Spleeter/UVR?) and whether they stream were not examined.
- No listening-test or SDR comparison between speech-enhancement plugins and separation models on "music with speech" material was found.
