# Android root / system-privileged approaches to intercepting ALL app audio, processing it (NN instrument removal), and outputting only the processed signal (state: late 2026)

Scope note: rootless approaches (MediaProjection/AudioPlaybackCapture in a normal app) are covered by another researcher. This note covers only paths that need root (Magisk/KernelSU/APatch), a custom ROM, a priv-app with privileged permissions, platform signing, or shell (uid 2000) privileges. All AOSP quotes are from `refs/heads/main` as of 2026-11-06 unless noted. Web-search budget was exhausted near the end; remaining gaps are listed per section.

---

## Key Question 1 — Custom audio-effect libraries (ViPER4Android, JamesDSP root, AML): how they are wired, where they execute, constraints, offload, BT/USB, Android 12–16 / Samsung issues, maintenance status

### Takeaway
A native effect `.so` declared in the vendor effects config (`/vendor/etc/audio_effects.xml`, or `audio_effects_config.xml` for the Android 14+ AIDL effect HAL) is loaded by the **vendor audio-HAL service process** (`/vendor/bin/hw/android.hardware.audio.service`, SELinux domain `hal_audio_default`, running as user `audioserver`), not by `audioserver` itself; AudioFlinger calls its `process()` once per mixer period (>= 20 ms) through an FMQ. It only sees PCM that goes through the software MIXER thread: the framework itself forces offloaded music tracks back to the mixer when a non-offloadable effect is enabled, DIRECT outputs reject effects, and fast tracks bypass software global effects. V4A/JamesDSP/AML are still installable in 2026 but effectively community-maintained, with new breakages on KernelSU mounting and (by inference) on devices that moved to the AIDL effect HAL.

### Cited Findings

**Config file, format, and library locations**
- The default effects file is `/vendor/etc/audio_effects.xml`; "To set your own defaults, create this file." Reference examples: `device/samsung/manta/audio_effects.xml` and `/device/google/crosshatch/audio_effects.xml`. The `<preprocess>` section maps capture sources (`voice_communication` -> `aec`, `ns`; `camcorder` -> `agc`) and "Declaring effects this way makes the framework request them from the HAL automatically." — [AOSP: Implement pre-processing effects](https://source.android.com/docs/core/audio/implement-pre-processing)
- The AOSP reference `media/libeffects/data/audio_effects.xml` has sections `libraries` (name + `.so` path, "located in `/vendor/lib/soundfx` on the target"), `effects` (name -> library + implementation UUID), and commented-out `preprocess`, `postprocess` (valid stream types: music, ring, alarm, notification, voice_call) and `deviceEffects` (effects attached to device ports; "the framework enables them by default and adds them automatically when the port is part of an audio patch. HW patches require hardware-accelerated effects"). Offloadable effects use an `effectProxy` element containing a `libsw` (software) and a `libhw` (DSP) sub-element, each with its own `uuid` and `library`; `libeffectproxy.so` must be listed alongside. — [AOSP audio_effects.xml](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/media/libeffects/data/audio_effects.xml)
- Pixel (redbull) vendor config maps `"offload_bundle"` -> `libqcompostprocbundle.so` and `"proxy"` -> `libeffectproxy.so`; bramble's `effectProxy` entries pair a `libsw` with a `libhw` pointing at `offload_bundle` (e.g. virtualizer). — [device/google/redbull audio_effects.xml](https://android.googlesource.com/device/google/redbull/+/b53cd6a/audio/audio_effects.xml); [device/google/bramble audio_effects.xml](https://android.googlesource.com/device/google/bramble/+/e0be56f%5E/audio/audio_effects.xml)
- Config search order used by the audio HAL/framework helper `audio_find_readable_configuration_file()`: `{"/odm/etc", "/vendor/etc", "/system/etc"}` (with `/vendor/etc/audio/sku_<ro.boot.product.vendor.sku>` inserted after `/odm/etc` when that property is set). — [system/media audio_config.h](https://android.googlesource.com/platform/system/media/+/refs/heads/main/audio/include/system/audio_config.h)

**Android 14+ AIDL effect HAL changes the file name and the library ABI**
- "Starting with Android 14, partners and SoC vendors are encouraged to replace the current HIDL HAL implementation" with AIDL; in AIDL "the `effectProxy` logic defined in XML files in HIDL Effects HAL is moved to the audio framework", and the mapping table lists `audio_effects.xml` -> `IFactory.queryProcessing` / `IFactory.queryEffects`. — [AOSP: AIDL and HIDL audio HAL comparison](https://source.android.com/docs/core/audio/aidl-hidl-comp)
- The AOSP AIDL effect HAL service (`EffectMain.cpp`) looks for `kDefaultConfigName = "audio_effects_config.xml"` (first inside a vendor APEX `.../etc/`, else via `audio_find_readable_configuration_file`), and logs `"config file audio_effects_config.xml not found!"` otherwise. — [hardware/interfaces audio/aidl/default/EffectMain.cpp](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/audio/aidl/default/EffectMain.cpp)
- AIDL library search path: `#define SOUND_FX_PATH "/lib64/soundfx/"` (LP64) or `"/lib/soundfx/"`, with `kEffectLibPath[] = { "/odm" SOUND_FX_PATH, "/vendor" SOUND_FX_PATH, "/system" SOUND_FX_PATH }`. — [EffectConfig.h](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/audio/aidl/default/include/effectFactory-impl/EffectConfig.h)
- The AIDL `Factory` `dlopen()`s each library and `dlsym()`s the symbol `"createEffect"` (`EffectCreateFunctor`) and a `queryEffectFunc`; failure returns `EX_NULL_POINTER "dlNullcreateEffectFunc"`. — [EffectFactory.cpp](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/audio/aidl/default/EffectFactory.cpp)
- The AIDL example config says: "Existing audio_effects.xml should working without any change as long as: 1. 'path' attribute of 'library' element matches with the actual effect library name. 2. 'name' attribute of 'effect' and 'effectProxy' element correctly added as key of kUuidNameTypeMap ... 3. 'uuid' attribute of 'effect' element matches Identity.uuid in Descriptor.aidl", and all its libraries are AIDL builds (`libbundleaidl.so`, `libequalizersw.so`, ...). — [audio_effects_config.xml (AIDL example)](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/audio/aidl/default/audio_effects_config.xml)
- Framework side, `libaudiohal` probes for `android.hardware.audio.effect` `IFactory` (AIDL) before `IEffectsFactory` (HIDL) and picks the HAL type that is registered. — [frameworks/av libaudiohal/FactoryHal.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/media/libaudiohal/FactoryHal.cpp)

**Which process actually runs the effect (not audioserver)**
- The HIDL audio HAL service binary registers both `android.hardware.audio@X::IDevicesFactory` and `android.hardware.audio.effect@4.0..7.0::IEffectsFactory` as passthrough implementations in the same vendor process. — [service.cpp](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/audio/common/all-versions/default/service/service.cpp)
- Its init script: `service vendor.audio-hal /vendor/bin/hw/android.hardware.audio.service`, `class hal`, `user audioserver`, `capabilities BLOCK_SUSPEND SYS_NICE`, `rlimit rtprio 10 10`, `ioprio rt 4`, `task_profiles ProcessCapacityHigh HighPerformance`, `onrestart restart audioserver`. — [android.hardware.audio.service.rc](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/audio/common/all-versions/default/service/android.hardware.audio.service.rc)
- Effect `process()` between framework and HAL is done through FMQ: the AIDL client "writes input into an FMQ, waits on a status queue, and then reads output from another FMQ"; the HIDL `IEffect.process` was re-implemented "using FMQ and IMemory, so there are no hwbinder calls during music processing". — [EffectHalAidl.cpp](https://android.googlesource.com/platform/frameworks/av/+/main/media/libaudiohal/impl/EffectHalAidl.cpp); [HIDL IEffect.hal (FMQ TODO)](https://gerrit.omnirom.org/plugins/gitiles/android_hardware_interfaces/+/4c0d397f1c9268baa56a1e4b0521418423f0883c/audio/effect/2.0/IEffect.hal)
- SELinux: `hal_audio_default` is `hal_server_domain(hal_audio_default, hal_audio)`, `hal_client_domain(hal_audio_default, hal_allocator)`, may `find` `fwk_sensor_service`. — [vendor/hal_audio_default.te](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/vendor/hal_audio_default.te). The `hal_audio` attribute policy grants only `ion_device:chr_file r_file_perms`, `audio_device` dir/chr rw, `r_dir_file(hal_audio, proc)`, `r_dir_file(hal_audio, proc_asound)`, `appdomain:fd use`, `sys_nice`, and has `neverallow hal_audio_server { file_type fs_type }:file execute_no_trans;` — no `gpu_device`, no `hal_neuralnetworks`, no sdcard/app-data rules. — [private/hal_audio.te](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/hal_audio.te)
- For comparison `audioserver` itself: `r_dir_file(audioserver, sdcard_type)`, `r_dir_file(audioserver, fuse)` (read-only storage), `audio_data_file` create, `hal_client_domain(audioserver, hal_audio)`; `neverallow audioserver { file_type fs_type }:file execute_no_trans;` and no TCP/UDP sockets. — [private/audioserver.te](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/audioserver.te)
- Community SELinux rules needed by V4A on Android 14 ROM builds: `allow audioserver unlabeled:file { read write open getattr };`, `get_prop(audioserver, vendor_audio_prop)`, `allow hal_audio_default hal_audio_default:process { execmem };`, `get_prop(hal_audio_default, vendor_audio_prop)`, `set_prop(hal_audio_default, vendor_audio_prop)`; the XML entries are `<library name="v4a_fx" path="libv4a_fx.so"/>` and `<effect name="v4a_standard_fx" library="v4a_fx" uuid="41d3c987-e6cf-11e3-a88a-11aba5d5c51b"/>`; "Works only on Android-14" (separate branch for Android 13 and lower). — [packages_apps_ViPER4AndroidFX (gitea mirror)](https://gitea.com/hdzungx/packages_apps_ViPER4AndroidFX)

**Where in AudioFlinger effects run, and what they do NOT see**
- In `PlaybackThread::threadLoop()`: `// only process effects if we're going to write` / `if (mSleepTimeUs == 0 && mType != OFFLOAD) { for (...) effectChains[i]->process_l(); ...}` — software effect chains are processed in the playback thread loop and skipped on OFFLOAD threads. — [services/audioflinger/Threads.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audioflinger/Threads.cpp)
- `PlaybackThread::checkEffectCompatibility_l()`: on `MIXER` threads with a fast mixer, `// global effects are applied only to non fast tracks if they are SW` (session `AUDIO_SESSION_OUTPUT_MIX` without `EFFECT_FLAG_HW_ACC_TUNNEL`); `AUDIO_SESSION_OUTPUT_STAGE` / `AUDIO_SESSION_DEVICE` accept only `EFFECT_FLAG_TYPE_POST_PROC` effects; `case OFFLOAD: // nothing actionable ... is NOT offloadable: the effect should still be created, but EffectHandle::enable() will take care of invalidating the tracks of the thread`; `case DIRECT: // Reject any effect on Direct output threads for now, since the format of mSinkBuffer is not guaranteed to be compatible with effect processing (PCM 16 stereo).`; `DUPLICATING` rejects global and post-proc effects; `SPATIALIZER` threads support global effects only on spatialized tracks. — [Threads.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audioflinger/Threads.cpp)
- `AudioFlinger::onNonOffloadableGlobalEffectEnable()` iterates playback threads and for every `OFFLOAD` thread calls `invalidateTracks(AUDIO_STREAM_MUSIC)`; `isNonOffloadableGlobalEffectEnabled_l()` checks the `AUDIO_SESSION_OUTPUT_MIX` chain of each thread. — [AudioFlinger.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audioflinger/AudioFlinger.cpp)
- Audio policy: `// Do not allow offloading if one non offloadable effect is enabled or MasterMono is enabled. // This prevents creating an offloaded track and tearing it down immediately after start when audioflinger detects there is an active non offloadable effect.` guarded by `if (((flags & AUDIO_OUTPUT_FLAG_COMPRESS_OFFLOAD) == 0) || !(mEffects.isNonOffloadableEffectEnabled() || mMasterMono))`; also `//force direct flag if offload flag is set: offloading implies a direct output stream`. — [AudioPolicyManager.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audiopolicy/managerdefault/AudioPolicyManager.cpp)
- `EffectDescriptorCollection::isNonOffloadableEffectEnabled()` returns true when an effect is `mEnabled && isMusicEffect() && (mDesc.flags & EFFECT_FLAG_OFFLOAD_SUPPORTED) == 0`, logging `"non offloadable effect %s, uuid %s, enabled on session %d"`. — [EffectDescriptor.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audiopolicy/common/managerdefinitions/src/EffectDescriptor.cpp)
- Historic commit text: "offloading is not allowed if one non offloadable effect is enabled"; a later change made output-stage effects ignored for this check (for spatial audio). — [libhardware_legacy commit](https://android.googlesource.com/platform/hardware/libhardware_legacy/+/000bb51%5E%21/); [frameworks_av commit (e/OS mirror)](https://gitlab.e.foundation/e/os/android_frameworks_av/-/commit/a8a4eeb95988e6bb73f7a742c8dd238c1f96c5c4)
- Qualcomm HAL property `audio.offload.disable=true` disables all offload; `audio.offload.compress.disable` disables compressed offload only. — [FP4 hardware_qcom_audio commit (e/OS)](https://gitlab.e.foundation/e/devices/FP4/android_hardware_qcom_audio/-/commit/0ac0903e86527d37108fe8da3075242fb0daf5c8)
- Latency design: "There is always a normal mixer thread"; normal mixer period "is computed to be the first integral multiple of the fast mixer period that is >= 20 ms"; fast mixer "recommended period of two to three milliseconds"; fast mixer "Omitted features: Per track sample rate conversion, Per track effects, Per mix effects"; effects processing is listed under the normal mixer. — [AOSP latency design](https://source.android.com/docs/core/audio/latency/design)
- 2012 AOSP engineer: "Effects are applied to normal tracks only, not fast tracks ... applied by the normal mixer, prior to entering the fast mix." — [android-porting list](https://mail-archive.com/android-porting@googlegroups.com/msg18557.html)

**Session 0 / global output mix**
- Equalizers originally attached effects to session 0 (global output mix); Google deprecated this "less than a year after Gingerbread's initial release" citing "too many problems with supporting global effects", but "the method was never fully removed, and some devices still support it." V4A "pushes the libv4a_fx.so audio effect library to /vendor/lib/soundfx" and "patches audio_effects.xml in /vendor/etc to define the v4a_fx audio effect." Per-app session IDs are hard to obtain for other apps' players; YouTube "only logs its audio session ID for debugging purposes." — [Esper: Why Android equalizer apps are inconsistent](https://www.esper.io/blog/android-equalizer-apps-inconsistent)

### Inferences
- Execution context for a custom NN effect: it runs inside the vendor HAL process (`hal_audio_default`, user `audioserver`, `rtprio 10`), is called synchronously from AudioFlinger's playback thread via FMQ, and must return within one mixer period (>= 20 ms, typically 20–40 ms at 48 kHz) or the mixer underruns. There is no Java runtime in that process. Loading model weights requires the file to be readable by `hal_audio_default`: the stock policy grants no sdcard/app-data access, so weights must ship inside the module's `/vendor` (or `/odm`) overlay or sepolicy must be extended (`magiskpolicy`/`sepolicy.rule`) — exactly what V4A's community rules already do for `execmem`/`unlabeled` files.
- GPU/NPU from inside the effect: stock `hal_audio` policy has no `gpu_device` or `hal_neuralnetworks` client rules, so NNAPI/GPU delegates would be SELinux-denied unless the module injects additional `allow` rules; the `neverallow ... execute_no_trans` rule also prevents spawning helper executables from that domain. Technically possible with root sepolicy patches, but untested in any project found.
- Bitness: the effect `.so` must match the HAL service's bitness (`/lib64/soundfx` for LP64 HAL); modern devices run 64-bit vendor HALs, hence the Huawei "64-bit lib" note.
- Offload: the framework, not V4A, is what "disables offload" — enabling any non-`EFFECT_FLAG_OFFLOAD_SUPPORTED` music effect on session 0 makes AudioPolicyManager refuse new `COMPRESS_OFFLOAD` outputs and makes AudioFlinger invalidate `AUDIO_STREAM_MUSIC` tracks on OFFLOAD threads, so players re-create their tracks on the PCM mixer path where the effect runs. Cost: higher power, and a brief glitch at the moment of invalidation. A root module can additionally force `audio.offload.disable=true` (Qualcomm HAL) so the offload path is never attempted.
- DIRECT outputs (e.g., hi-res/USB-DAC direct PCM, passthrough) reject software effects outright; audio that an app plays through a DIRECT output will bypass the NN effect. Fast tracks bypass software global effects (only HW-tunneled effects apply to them), so low-latency game/Oboe audio using `AUDIO_OUTPUT_FLAG_FAST` will not be processed.
- Bluetooth/USB: software effects on the MIXER thread are applied before the A2DP/USB HAL, so they should apply, but V4A issue #39 "Does not process Bluetooth audio" shows OEM configurations where the BT output is a separate (offload/direct) output profile that bypasses the mixer effect chain; treat BT as device-dependent.
- AIDL effect HAL risk (Android 14+ devices whose vendor shipped the AIDL effect HAL): the AIDL factory `dlsym`s `createEffect`/`queryEffect` and reads `audio_effects_config.xml`, whereas legacy V4A/JamesDSP libraries implement the legacy `effect_interface` (`AUDIO_EFFECT_LIBRARY_INFO_SYM`) and are declared in `audio_effects.xml`; on such devices the legacy libraries will not load unless the vendor still exposes the HIDL `IEffectsFactory`. This likely underlies the Pixel "Driver not found"/"Unsupported" reports but no source confirms the root cause.
- Maintenance in 2026: V4A's official driver is closed-source and last changed around app v0.6.1/0.6.2 (fix for Android 14); JamesDSP's root path is kept alive mainly by the RootlessJamesDSP maintainer's untested root builds and the `ainur_jamesdsp` module; AML is maintained by forks. All three are community-maintained with no OEM-version guarantees.

## Key Question 2 — `REMOTE_SUBMIX` capture with `CAPTURE_AUDIO_OUTPUT`: granting it, the reroute/silence behaviour, exclusions, interaction with `allowAudioPlaybackCapture`, and scrcpy's mechanisms (`output` vs `playback`, `--audio-dup`)

### Takeaway
`REMOTE_SUBMIX` is a virtual output device: when a `CAPTURE_AUDIO_OUTPUT` holder opens an input on it (address "0"), AudioPolicyManager connects `AUDIO_DEVICE_OUT_REMOTE_SUBMIX` and the default engine routes MEDIA/DTMF/ACCESSIBILITY/REROUTING/ENFORCED_AUDIBLE strategies to it instead of the speaker; SONIFICATION (ring/alarm/notification) and PHONE are not rerouted. The captured stream is not subject to the per-app `allowAudioPlaybackCapture` opt-out (that governs the MediaProjection/AudioPlaybackCapture path only); the device goes silent for the rerouted streams, which is exactly what a "process and re-emit" design needs. scrcpy proves both mechanisms from uid 2000 (shell) without a consent dialog: `--audio-source=output` = `REMOTE_SUBMIX` (Android 11+, device muted), `--audio-source=playback` = hidden `AudioPolicy`/`AudioMix` API (Android 13+, apps can opt out), with `--audio-dup` (scrcpy 2.6, Aug 2024) using `ROUTE_FLAG_LOOP_BACK_RENDER` to keep audio playing on the device.

### Cited Findings

**API contract**
- `MediaRecorder.AudioSource.REMOTE_SUBMIX` (API 19, value 8): "An application can use this audio source to capture a mix of audio streams that should be transmitted to a remote receiver such as a Wifi display. While recording is active, these audio streams are redirected to the remote submix instead of being played on the device speaker or headset. Certain streams are excluded from the remote submix, including `STREAM_RING`, `STREAM_ALARM`, and `STREAM_NOTIFICATION`. These streams will continue to be presented locally as usual. Capturing the remote submix audio requires the `CAPTURE_AUDIO_OUTPUT` permission. This permission is reserved for use by system components and is not available to third-party applications." `VOICE_CALL`, `VOICE_UPLINK`, `VOICE_DOWNLINK` also require `CAPTURE_AUDIO_OUTPUT`. `VOICE_PERFORMANCE` (API 29) "will minimize latency and coupling with playback path." — [MediaRecorder.AudioSource](https://developer.android.com/reference/android/media/MediaRecorder.AudioSource)

**scrcpy's two capture paths**
- Doc: "Audio forwarding is supported for devices with Android 11 or higher"; Android 12+: "it works out-of-the-box"; Android 11: "you'll need to ensure that the device screen is unlocked when starting scrcpy. A fake popup will briefly appear to make the system think that the shell app is in the foreground. Without this, audio capture will fail"; Android 10 or earlier: "audio cannot be captured and is automatically disabled". Sources: `output` (default, REMOTE_SUBMIX), `playback` (Android 13+), `mic*`, `voice-call`, `voice-call-uplink`, `voice-call-downlink`, `voice-performance`. "`--audio-dup` ... supports keeping the audio playing on the device while mirroring" and implies `--audio-source=playback`. — [scrcpy doc/audio.md](https://github.com/Genymobile/scrcpy/blob/master/doc/audio.md)
- `AudioDirectCapture.java`: builds a public `AudioRecord.Builder` with `setContext(FakeContext.get())` on API 31+, buffer `8 * minBufferSize` ("This buffer size does not impact latency"), Vivo fallback via `Workarounds.createAudioRecord`; Android 11 workaround starts `com.android.shell.HeapDumpActivity` because the server "has the same user ID (2000)" as the shell app and the permission system treats it as foreground; error text "On Android 11, audio capture must be started in the foreground". — [AudioDirectCapture.java](https://github.com/Genymobile/scrcpy/blob/master/server/src/main/java/com/genymobile/scrcpy/audio/AudioDirectCapture.java)
- `AudioPlaybackCapture.java`: no `MediaProjection`; builds `AudioMixingRule` (`MIX_ROLE_PLAYERS`, `RULE_MATCH_ATTRIBUTE_USAGE` for 13 usages incl. - `AudioMix` javadoc: `ROUTE_FLAG_RENDER` "output of the mix is sent to the original destination"; `ROUTE_FLAG_LOOP_BACK` "rerouted back to the framework and is accessible for injection or capture through the AudioTrack and AudioRecord APIs"; `ROUTE_FLAG_LOOP_BACK_RENDER` (`@hide`) "the targeted audio is played unaffected but a copy is accessible for capture through AudioRecord ... ### Inferences
- Exact behaviour of the legacy REMOTE_SUBMIX (address "0") path for a "mute-and-replace" app: once your `AudioRecord(REMOTE_SUBMIX)` starts, the engine moves MEDIA-strategy playback (music, video, YouTube, games, TTS/accessibility, DTMF, enforced-audible) to the r_submix virtual device; speaker/headset/BT/USB receive nothing from those streams; ring/alarm/notification and in-call audio stay local and are not captured. Your own re-emitted `AudioTrack` must NOT be MEDIA-strategy or it will also be rerouted into the submix (feedback). Options: play it with a non-rerouted strategy/usage (e.g. an attribute mapped to SONIFICATION/ENFORCED_AUDIBLE — note ENFORCED_AUDIBLE is also rerouted in the engine block above, so SONIFICATION-type usages such as `USAGE_NOTIFICATION`/`ALARM`-mapped attributes are the ones routed locally), or use an `AudioMix` (policy-mix) design with `excludeUid(ownUid)` instead of the legacy global submix. This design choice is not documented by any project found; it must be validated on-device.
- App opt-outs (`allowAudioPlaybackCapture="false"`, `ALLOW_CAPTURE_BY_NONE`) and `AUDIO_FLAG_NO_MEDIA_PROJECTION` gate only MediaProjection-backed loopback mixes; the legacy REMOTE_SUBMIX reroute is device routing by strategy and is not filtered per app — consistent with scrcpy's `output` mode forwarding "the whole audio output" while `playback` is opt-out-able. YouTube/Spotify therefore are captured by REMOTE_SUBMIX (as on Wi-Fi Display), subject to the DRM caveat below.
- scrcpy works without consent because its server runs as uid 2000 (shell) via `app_process`, and the Shell package holds `CAPTURE_AUDIO_OUTPUT` and `MODIFY_AUDIO_ROUTING`; the hidden-API reflection works because the server is not a zygote-spawned app. A root-privileged project can do the same by running a helper as shell/root via `app_process`, or by systemizing an app with `privapp-permissions`, or by platform-signing on a custom ROM.
- Latency floor of the submix loopback: the r_submix pipe (4096 frames at 48 kHz ~ 85 ms capacity, 4 periods -> ~21 ms minimum) plus AudioRecord buffering, plus NN processing, plus the re-emitted AudioTrack through the normal mixer (>= 20 ms) and HAL. Expect >= 60–100 ms end-to-end before model latency; acceptable for music listening, visibly out of sync for video unless the video player's A/V sync compensates (it cannot, since the delay is invisible to it).
- `ROUTE_FLAG_LOOP_BACK_RENDER` (the `--audio-dup` mechanism) is useless for muting because the original keeps playing; `ROUTE_FLAG_LOOP_BACK` (silencing) via a registered `AudioPolicy` is the modern, per-usage-selectable equivalent of REMOTE_SUBMIX and needs `MODIFY_AUDIO_ROUTING` (shell/priv-app/platform) — it also lets you exclude your own uid.

### Gaps
- No AOSP source was found that explicitly states whether DRM/`AUDIO_OUTPUT_FLAG_DIRECT`-protected streams are excluded from the legacy REMOTE_SUBMIX reroute; scrcpy #4380 mentions "commented-out flags can capture audio from protected apps, but at very low quality" without detail. Treat DRM-protected (e.g. Netflix/Widevine L1 with secure audio) output as unverified.
- The `AudioService.java` side of `registerAudioPolicy` (the `MODIFY_AUDIO_ROUTING`-vs-projection check and the `MIX_ROUTE_FLAG_LOOP_BACK` permission for non-projection callers) was not fetched.
- No open-source project was found that performs REMOTE_SUBMIX capture, processes, and re-injects on the same device (internal-audio recorders and scrcpy only forward/record).

## Key Question 3 — Audio policy / AudioFlinger hacks: `MODIFY_AUDIO_ROUTING` + `AudioMix` loopback, custom `audio_policy_configuration.xml`, ALSA `snd-aloop`, custom HAL wrapper, LSPosed/Xposed hooking of `AudioTrack.write`

### Takeaway
The only hack-class approaches with working precedent are (a) `AudioPolicy`/`AudioMix` loopback mixes (scrcpy, system-API, `MODIFY_AUDIO_ROUTING`) and (b) a vendor-side effect library (Q1). `snd-aloop`-style kernel loopback has no Android precedent and is invisible to the HAL/policy stack; Xposed hooking of `AudioTrack.write` is per-process, misses native (AAudio/OpenSL/`MediaPlayer`-in-mediaserver) paths, and LSPosed itself is now a community fork (JingMatrix/Vector) with Android 16 support as of July 2025.

### Cited Findings
- `AudioMix` route flags and `@SystemApi` status; `ROUTE_FLAG_LOOP_BACK` makes mix output "accessible for injection or capture through the AudioTrack and AudioRecord APIs". — [AudioMix.java](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/media/java/android/media/audiopolicy/AudioMix.java)
- `registerPolicyMixes()` requires `MODIFY_AUDIO_ROUTING` unless the mix is `loopback|render` with a MediaProjection; `EXT_POLICY_REROUTE` inputs require `MODIFY_AUDIO_ROUTING`; `CAPTURE` mixes require `CAPTURE_AUDIO_OUTPUT`. — [AudioPolicyInterfaceImpl.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audiopolicy/service/AudioPolicyInterfaceImpl.cpp)
- AudioPolicyManager: registering a LOOP_BACK mix adds input/output profiles to the `AUDIO_HARDWARE_MODULE_ID_REMOTE_SUBMIX` module ("audio flinger mixer does not support mono output: configure remote submix HAL" note) and connects both `AUDIO_DEVICE_OUT_REMOTE_SUBMIX`/`AUDIO_DEVICE_IN_REMOTE_SUBMIX` for the mix address; "LOOP_BACK and LOOP_BACK | RENDER have the same remote submix backend". — [AudioPolicyManager.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audiopolicy/managerdefault/AudioPolicyManager.cpp)
- scrcpy's `AudioPlaybackCapture` implements exactly this via hidden `AudioManager.registerAudioPolicyStatic` and `AudioPolicy.createAudioRecordSink` from uid 2000. — [AudioPlaybackCapture.java](https://github.com/Genymobile/scrcpy/blob/master/server/src/main/java/com/genymobile/scrcpy/audio/AudioPlaybackCapture.java)
- Shell uid holds `MODIFY_AUDIO_ROUTING`, `MANAGE_AUDIO_POLICY`, `CAPTURE_AUDIO_OUTPUT`. — [Shell AndroidManifest.xml](https://android.googlesource.com/platform/frameworks/base/+/refs/heads/main/packages/Shell/AndroidManifest.xml)
- A2DP offload can be turned off at config level (`audio_policy_configuration_a2dp_offload_disabled.xml` device config) — shows `audio_policy_configuration.xml` mixPorts/routes are the lever for offload paths. — [StatiXOS bonito config](https://www.github.com/StatiXOS/android_device_google_bonito/blob/sc-v2/audio_policy_configuration_a2dp_offload_disabled.xml)
- The r_submix policy config fragment is `r_submix_audio_policy_configuration.xml` in `services/audiopolicy/config`. — [r_submix_audio_policy_configuration.xml](https://android.googlesource.com/platform/frameworks/av/+/c48ef75/services/audiopolicy/config/r_submix_audio_policy_configuration.xml)
- ALSA `snd-aloop` on Android: a developer whose `snd-aloop` card appeared in ALSA tools found it "was not visible to apps when it was the only sound card loaded"; a reply suggested opening the PCM node directly from HAL code; no confirmed fix. — [android-platform thread](https://groups.google.com/g/android-platform/c/UN14RW7rGXQ)
- Xposed hooking: `AudioTrack.write` is an app-side call ("streaming of PCM audio buffers to the audio sink for playback"); a hook there covers only the processes it is scoped to; XAudioCapture hooks the system package to change capture policy rather than audio content. — [LSPosed discussion #1187](https://github.com/orgs/LSPosed/discussions/1187); [XAudioCapture](https://github.com/wzhy90/XAudioCapture)
- AAudio "is a new Android C API introduced in the Android O release ... Apps communicate with AAudio by reading and writing data to streams"; Oboe "calls AAudio when it is available, and falls back to OpenSL ES"; `AAUDIO_SHARING_MODE_EXCLUSIVE` streams "have exclusive access to its audio device"; `AAUDIO_PERFORMANCE_MODE_LOW_LATENCY` "uses smaller buffers and an optimized data path". — [AAudio guide](https://developer.android.com/ndk/guides/audio/aaudio/aaudio)
- LSPosed status: the original project "is no longer maintained"; the JingMatrix fork v1.10.2 (July 2025) "listed full support for Android 16"; a discussion under `JingMatrix/Vector` (apparent rename) has mixed Android 16 reports (Pixel 7 Pro failures vs. "works perfectly"). — [JingMatrix/Vector discussion #307](https://github.com/JingMatrix/Vector/discussions/307); [awesome-android-root LSPosed guide](https://awesome-android-root.pages.dev/rooting-guides/lsposed-guide)

### Inferences
- `AudioMix` loopback (ROUTE_FLAG_LOOP_BACK, `MIX_ROLE_PLAYERS`, match usages MEDIA/GAME/UNKNOWN/ASSISTANT/..., `excludeUid(self)`) is the cleanest root-level capture: it silences only the matched usages, avoids feedback by uid exclusion, and is already proven from shell by scrcpy on Android 13+. It still inherits the per-app `allowAudioPlaybackCapture`/`AUDIO_FLAG_NO_MEDIA_PROJECTION` opt-out semantics unless the policy is registered without a projection by a `MODIFY_AUDIO_ROUTING` holder — whether opt-out is enforced for non-projection system mixes was not verified.
- A custom `audio_policy_configuration.xml` that routes all output into r_submix and back is equivalent to the above but static, fragile across OEM configs, and would break calls/alarms unless carefully scoped; no project found doing this.
- `snd-aloop`: Android HALs open specific PCM nodes from `mixer_paths.xml`/HAL code; a loopback card is invisible to the policy stack without a HAL change, so this needs a custom (or wrapper) audio HAL — effectively a custom ROM. No precedent found.
- Custom HAL wrapper (a vendor `IModule`/`IDevicesFactory` shim that intercepts `write()` of the primary output): technically the most complete (sees everything incl. offloaded PCM after decode? no — compressed offload streams bypass PCM writes entirely), but requires replacing a vendor binary and matching the OEM's HAL ABI; no open-source precedent found.
- Xposed/LSPosed `AudioTrack.write` hooking: requires injecting into every media process (Zygisk), misses AAudio/OpenSL/MMAP exclusive streams, `MediaPlayer` output rendered inside `mediaserver`, and offloaded tracks; adds per-app memory for the model, and cannot provide a single global mix. Not viable for a system-wide guarantee.

### Gaps
- Whether `AUDIO_FLAG_NO_MEDIA_PROJECTION` (app opt-out) is honoured for `AudioMix` loopback registered by a `MODIFY_AUDIO_ROUTING` holder without a projection was not confirmed from source (`AudioPolicyMix.cpp` not fetched).
- No benchmark or project measuring the end-to-end latency of an AudioMix-loopback -> process -> AudioTrack chain on Android.

## Key Question 4 — Compute budget: can a 50–500 MFLOP/frame separation model run inside the effect thread, or must audio be shipped to a separate NN process; latency added; precedents for effects calling another process

### Takeaway
The effect `process()` callback runs synchronously in the vendor HAL process once per mixer period (>= 20 ms) on a `SYS_NICE`/rtprio thread with no GPU/NNAPI SELinux access by default; a lightweight CPU model (tens of MFLOP/frame) can fit, but hundreds of MFLOP/frame or NPU use realistically means handing the block to a separate process over shared memory, adding at least one extra block period of latency. The framework already does per-buffer cross-process effect I/O (AudioFlinger <-> HAL via FMQ), which is the only well-documented precedent; vendor-claimed on-device separation latencies are 11–100 ms and are not independently verified.

### Cited Findings
- Effect processing happens in the normal mixer path, period >= 20 ms; the fast mixer omits per-track and per-mix effects. — [AOSP latency design](https://source.android.com/docs/core/audio/latency/design)
- The HAL service runs with `capabilities BLOCK_SUSPEND SYS_NICE`, `rlimit rtprio 10 10`, `ioprio rt 4`, `task_profiles ProcessCapacityHigh HighPerformance`. — [android.hardware.audio.service.rc](https://android.googlesource.com/platform/hardware/interfaces/+/refs/heads/main/audio/common/all-versions/default/service/android.hardware.audio.service.rc)
- Cross-process per-buffer precedent: effect `process()` is carried over FMQ + shared memory ("no hwbinder calls during music processing"; AIDL client writes input FMQ, waits status MQ, reads output FMQ). — [EffectHalAidl.cpp](https://android.googlesource.com/platform/frameworks/av/+/main/media/libaudiohal/impl/EffectHalAidl.cpp); [IEffect.hal](https://gerrit.omnirom.org/plugins/gitiles/android_hardware_interfaces/+/4c0d397f1c9268baa56a1e4b0521418423f0883c/audio/effect/2.0/IEffect.hal)
- `hal_audio` SELinux policy has no `gpu_device`/`hal_neuralnetworks` rules; `neverallow ... execute_no_trans`. — [private/hal_audio.te](https://android.googlesource.com/platform/system/sepolicy/+/refs/heads/main/private/hal_audio.te)
- `EffectDescriptorCollection::getMaxEffectsCpuLoad()` returns `MAX_EFFECTS_CPU_LOAD` (the policy tracks a CPU-load budget per effect descriptor). — [EffectDescriptor.cpp](https://android.googlesource.com/platform/frameworks/av/+/refs/heads/main/services/audiopolicy/common/managerdefinitions/src/EffectDescriptor.cpp)
- Vendor effect + separate HIDL service precedent: Sony Dolby Atmos device tree ships `vendor.dolby.hardware.dms@2.0-service` + its `.rc` and `vendor.dolby.hardware.dms@2.0` libs (32/64-bit) alongside `vendor/lib/soundfx/libswvqe.so`; a Magisk Dolby port "conflicts with the `vendor.dolby.hardware.dms@2.0-service`" package. — [Evolution-X hardware_dolby commit](https://git.evolution-x.org/Evolution-X-Devices/hardware_dolby/commit/a6202e7f90559dccc13e09ed4684a19d22fbd0f6); [Dolby Atmos OnePlus 9 Pro module](https://github.com/reiryuki/Dolby-Atmos-OnePlus-9-Pro-Magisk-Module)
- On-device separation latency claims (vendor, unverified): AudioShake SDK "end-to-end separation latency under 50ms", "up to 200x real-time", "models as small as 9mb", NPU/GPU/CPU runtimes; a DJ app blog claims "approximately 100ms of latency on a mid-range Android device and below 50ms on flagship devices with dedicated NPUs". — [AudioShake SDK](https://www.audioshake.ai/products/sdk); [DJ Pro blog](https://dynasty-x.pages.dev/blog/dj-pro-stem-separation-technology)
- Academic: VoiceBit — GPU-accelerated binarized real-time human-voice separation on mobile (speed/energy gains vs. SOTA frameworks; no ms figures in abstract). — [VoiceBit (ECNU)](https://pure.ecnu.edu.cn/en/publications/voicebit-gpu-accelerated-real-time-human-voice-separation-for-mob/)

### Inferences
- Arithmetic: at a 20 ms hop, 50 MFLOP/frame = 2.5 GFLOP/s sustained, 500 MFLOP/frame = 25 GFLOP/s. A single big ARM core with NEON delivers on the order of 10–30 GFLOP/s peak in fp32 and far less sustained under thermal limits, so ~50 MFLOP/frame is plausible in-thread (int8/fp16 helps), while ~500 MFLOP/frame is not safely achievable inside the HAL callback without starving the mixer; it would need multi-core or NPU — i.e., a separate process.
- Separate-process design: effect copies the block into shared memory (ashmem/dmabuf) + futex/FMQ to an NN daemon (root-launched, with its own sepolicy allowing GPU/NNAPI); to keep the mixer deterministic the effect must return the previous block's result (pipelining) — this adds exactly one block period (20–40 ms) plus jitter, on top of the model's own look-ahead/receptive-field latency. Same pattern as AudioFlinger<->HAL FMQ, so it is engineering-feasible; no open-source Android effect doing NN inference in another process was found.
- Memory/time constraints: the effect library is dlopen'ed in a process with `execute_no_trans` neverallow and (by default) no JIT; use static TFLite/ONNX/XNNPACK linked into the `.so` or into the daemon.

### Gaps
- No independent benchmark of any real-time instrument-removal model on a phone CPU/NPU was found; the only numbers are vendor marketing.
- No source for Dolby's actual effect<->DMS IPC contents (whether per-buffer audio or control only).

## Key Question 6 — Distribution reality: share of rooted users, Play Integrity, banking apps

### Takeaway
There is no reliable 2025–2026 statistic for the rooted share of Android users (the most-cited number is a 2014 Tencent study, 27.44%). Google now requires hardware-backed signals for all Play Integrity verdicts on Android 13+; rooted devices can at most return `MEETS_BASIC_INTEGRITY`, and the `MEETS_DEVICE_INTEGRITY` verdict needs a locked bootloader with a certified OEM image, which excludes rooted/custom-ROM devices unless they use hide/spoof modules (Zygisk Next + Play Integrity Fix/TrickyStore) that work only intermittently.

### Cited Findings
- Google: Play Integrity API "now requires hardware-backed security signals for all integrity verdicts on Android 13 and later"; "rooted devices are eligible to return meets-basic-integrity so long as key attestation is present"; the device verdict requires "hardware-backed proof that the device bootloader is locked and the loaded Android OS is a certified device manufacturer image". — [Improved verdicts (Android 13+)](https://developer.android.com/google/play/integrity/improvements); [Integrity verdicts](https://developer.android.com/google/play/integrity/verdict)
- 2026 community guidance: the "current 2026 module stack" is ZygiskNext + a Play Integrity Fix fork; works on Android 16 QPR1/QPR2 with Magisk and KernelSU; "strong integrity requires a locked bootloader"; "most banking apps only need DEVICE integrity", some add their own root detection. — [dev.to 2026 guide](https://dev.to/pranavpatel/rooting-your-android-in-2026-how-i-finally-passed-play-integrity-on-a-2018-oneplus-6t-4lhh); [Hide-Root-Guide](https://github.com/hyowonbernabe/Hide-Root-Guide); [Magisk v30 vs KernelSU v3 (2026)](https://thecustomrom.com/blog/magisk-v30-vs-kernelsu-v3)
- Root prevalence: Tencent 2014 study "27.44% mobile phone users root(ed) their phones" (China sample); a different Tencent-attributed figure of 80% for Chinese respondents; an older Android Authority figure of ~1 in 20 Android phones rooted; reader polls (38% of a Portuguese site's readers). — [Android Headlines](https://www.androidheadlines.com/?p=438232); [Softpedia](https://news.softpedia.com/news/80-of-China-s-Android-Smartphone-Users-Have-Rooted-their-Devices-in-2014-478428.shtml); [Android Authority poll](https://androidauthority.com/android-phone-rooted-poll-results-3225345)
- Granting `CAPTURE_AUDIO_OUTPUT` via `privapp-permissions` edits "will trip SafetyNet" (author's note). — [android-call-recorder issue #134](https://gitlab.com/axet/android-call-recorder/-/issues/134)

### Inferences
- A root-only product addresses a niche (low single-digit percent of users at best, skewed to enthusiasts), and every system-partition/vendor-overlay change increases Play Integrity exposure; Samsung users additionally lose Knox-gated features permanently. For a mass-market "mute instruments" product, root should be a power-user tier, not the primary path.

### Gaps
- No current (2024–2026) survey or Google figure for rooted-device share; all numbers are old or self-selected polls.
- No published data on what fraction of rooted users keep DEVICE integrity passing over time with spoof modules.
